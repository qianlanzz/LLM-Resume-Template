# 面试题汇总 — 任务队列 / Agent / RAG

---

## Part 1：任务队列（BullMQ / Celery / Redis）

### 基础概念

**Q：消息队列解决了什么问题？**
> 三个核心问题：
> 1. **异步解耦**：耗时任务不阻塞 HTTP 请求，立即返回 jobId
> 2. **削峰填谷**：突发流量由队列缓冲，Worker 按自身处理能力消费
> 3. **可靠性**：任务持久化到 Redis，进程崩溃后可恢复，不丢任务

**Q：BullMQ 的任务有哪些状态？**
> `waiting` → `active`（Worker 取走）→ `completed` / `failed`  
> 失败后根据 `attempts` 配置进入 `delayed`（等待重试）或 `failed`（超过重试次数）

**Q：如何防止任务重复执行？**
> 1. BullMQ 的 `jobId` 去重：相同 `jobId` 的任务不会重复入队
> 2. 幂等设计：任务本身设计为幂等，重复执行结果一致（如用 `upsert` 而非 `insert`）
> 3. 分布式锁：任务开始时加锁，完成后释放，防止多 Worker 并发执行同一任务

**Q：任务失败重试的退避策略是什么？**
> - **固定间隔**：每次重试等待固定时间，简单但可能造成重试风暴
> - **指数退避**：等待时间按 2^n 增长（1s, 2s, 4s, 8s...），减少对下游的冲击
> - **指数退避 + 抖动**：在指数退避基础上加随机抖动，防止多个任务同时重试

**Q：队列积压了怎么排查？**
> 1. 看 Worker 是否存活（心跳监控）
> 2. 看任务执行时长是否异常增长（P95 指标）
> 3. 看下游依赖（数据库、外部 API）是否有超时
> 4. 临时扩容 Worker 数量消化积压

**Q：死信队列（DLQ）是什么？**
> 超过最大重试次数的任务进入死信队列（BullMQ 中是 `failed` 状态）。死信队列的作用是：不丢弃失败任务，保留现场供人工排查，支持手动重新触发。

---

### 进阶问题

**Q：BullMQ 和 RabbitMQ 怎么选？**
> - **BullMQ**：基于 Redis，部署简单，适合中小规模，Node.js 生态友好，支持优先级队列、延迟任务、任务进度
> - **RabbitMQ**：专业消息中间件，支持复杂路由（Exchange/Binding），消息持久化更可靠，适合高可靠性要求的场景
> 
> 我的项目用 BullMQ 是因为已有 Redis，不想引入新中间件，且任务规模不大。

**Q：如何实现任务优先级？**
> BullMQ 支持 `priority` 参数（数字越小优先级越高），内部用 Redis Sorted Set 按优先级排序。高优先级任务会插队到队列前面。

**Q：Worker 并发数怎么设置？**
> 取决于任务类型：
> - **CPU 密集型**：并发数 ≈ CPU 核心数，避免上下文切换开销
> - **I/O 密集型**（网络请求、数据库查询）：并发数可以远大于 CPU 核心数，充分利用等待时间
> 
> 录题系统的 OCR 任务是 I/O 密集型（等待外部 API 返回），并发数设为 10-20。

## Part 2：LLM Agent

### 基础概念

**Q：什么是 ReAct 框架？**
> ReAct = Reasoning + Acting。LLM 在每一步先输出思考过程（Thought），再决定执行什么动作（Action），观察结果（Observation）后继续下一步。循环直到得出最终答案。核心思想是把推理和行动交替进行，而不是一次性生成答案。

**Q：Agent 和普通 LLM 调用有什么区别？**
> 普通调用是单次 request-response，输入 → 输出。Agent 是多轮循环：LLM 可以调用工具获取信息，根据工具返回结果继续推理，直到完成任务。Agent 有"主动获取信息"的能力，而普通调用只能依赖输入中已有的信息。

**Q：LangGraph 和 LangChain AgentExecutor 有什么区别？**
> AgentExecutor 是黑盒循环，不可见内部状态，难以在中间步骤插入自定义逻辑。LangGraph 把 Agent 建模为显式有向图（StateGraph），每个节点和边都可自定义，支持：
> - 条件路由（根据状态决定下一步）
> - 并行节点（多个工具同时执行）
> - 持久化 Checkpoint（跨会话恢复）
> - 人工介入（Human-in-the-loop）

**Q：工具调用（Tool Use / Function Calling）是怎么工作的？**
> 1. 把工具的名称、描述、参数 Schema（JSON Schema）注入 System Prompt
> 2. LLM 输出结构化的工具调用请求（`tool_calls` 字段），包含工具名和参数
> 3. 应用层解析 `tool_calls`，执行对应函数，获取返回值
> 4. 把工具返回值作为 `ToolMessage` 追加到消息列表，继续调用 LLM
> 5. LLM 根据工具结果决定继续调用工具还是直接回复

**Q：Agent 的上下文窗口满了怎么办？**
> 三种策略：
> 1. **截断**：直接丢弃最早的消息，简单但丢失信息
> 2. **摘要压缩**：把旧消息用 LLM 压缩成摘要，注入 System Message，保留语义
> 3. **外部记忆**：把历史对话存到向量数据库，按需检索相关片段注入上下文（RAG 记忆）
> 
> AgentBot 用的是摘要压缩，超过 40 轮后压缩旧消息，Token 用量降低约 60%。

**Q：如何评估 Agent 的效果？**
> - **任务完成率**：给定任务，Agent 能否正确完成
> - **工具调用准确率**：是否调用了正确的工具，参数是否正确
> - **步骤效率**：完成任务需要几轮工具调用（越少越好）
> - **幻觉率**：Agent 是否编造了不存在的工具调用或虚假信息

### 进阶问题

**Q：Multi-Agent 系统怎么设计？**
> 常见模式：
> - **Supervisor 模式**：一个主 Agent 负责任务分解和调度，子 Agent 负责执行具体任务
> - **流水线模式**：Agent A 的输出是 Agent B 的输入，串行处理
> - **并行模式**：多个 Agent 同时处理不同子任务，结果汇总
> 
> WikiAgent 用的是 Supervisor 模式：主 Agent 根据用户意图路由到 Ingest/Query/Health Check 子 Agent。

**Q：Agent 的安全问题有哪些？**
> 1. **Prompt Injection**：恶意内容通过工具返回值注入，操控 Agent 行为。防御：对工具返回值做内容过滤，不直接把外部内容拼入 System Prompt
> 2. **工具滥用**：LLM 幻觉导致调用危险工具（如删除文件）。防御：工具白名单、危险操作二次确认、沙盒限制
> 3. **信息泄露**：Agent 把敏感信息传给外部工具。防御：工具调用审计日志，敏感字段脱敏

**Q：如何让 Agent 的工具调用更可靠？**
> 1. **工具描述要精确**：描述清楚工具的用途、参数含义、返回格式，减少 LLM 误用
> 2. **参数校验**：工具入口做严格的参数类型和范围校验，返回清晰的错误信息
> 3. **重试机制**：工具调用失败时，把错误信息返回给 LLM，让它修正参数重试
> 4. **Few-shot 示例**：在 System Prompt 中给出工具调用的正确示例

**Q：MCP（Model Context Protocol）是什么？**
> Anthropic 提出的开放协议，定义了 LLM 与外部工具/数据源交互的标准接口。类似于 USB 接口标准：工具开发者按 MCP 规范暴露接口，任何支持 MCP 的 LLM 客户端都能直接使用，不需要为每个 LLM 单独适配。

## Part 3：RAG（检索增强生成）

### 基础概念

**Q：RAG 解决了什么问题？**
> LLM 的知识截止于训练数据，无法回答最新信息或私有知识库的问题。RAG 在生成前先检索相关文档，把检索结果注入 Prompt，让 LLM 基于最新/私有知识回答，同时减少幻觉。

**Q：RAG 的基本流程是什么？**
> 1. **离线索引**：文档切块 → 向量化（Embedding 模型）→ 存入向量数据库
> 2. **在线检索**：用户问题向量化 → 向量数据库 ANN 检索 Top-K 相关块
> 3. **生成**：把检索到的文本块 + 用户问题拼入 Prompt → LLM 生成回答

**Q：文档切块（Chunking）有哪些策略？**
> - **固定长度切块**：按字符数切，简单但可能切断语义
> - **按句子/段落切块**：保留语义完整性，但块大小不均匀
> - **递归切块**：先按段落切，太长再按句子切，兼顾语义和大小
> - **语义切块**：用 Embedding 相似度判断语义边界，效果最好但计算量大
> - **重叠切块**：相邻块有重叠（如 20% overlap），防止关键信息被切断

**Q：向量检索用什么相似度度量？**
> - **余弦相似度**：衡量向量方向的相似性，不受向量长度影响，最常用
> - **内积（Dot Product）**：余弦相似度的未归一化版本，向量已归一化时等价
> - **L2 距离（欧氏距离）**：衡量向量空间距离，适合某些特定 Embedding 模型

**Q：FAISS 是什么？有哪些索引类型？**
> Facebook 开源的向量相似度搜索库，支持十亿级向量的高效检索。
> - **IndexFlatL2 / IndexFlatIP**：暴力搜索，精确但慢，适合小规模
> - **IndexIVFFlat**：倒排索引，先聚类再搜索，速度快但有精度损失
> - **IndexHNSW**：基于图的近似最近邻，速度和精度平衡好，内存占用大
> - **IndexIVFPQ**：量化压缩，内存占用最小，适合超大规模

**Q：RAG 效果不好怎么排查？**
> 分两个阶段排查：
> 1. **检索阶段**：检索到的文档是否相关？用 Recall@K 评估。问题：切块粒度不对、Embedding 模型不匹配领域、Top-K 太小
> 2. **生成阶段**：检索到了相关文档，但 LLM 没有正确利用？问题：Prompt 设计不好、文档太长超出上下文、文档顺序影响注意力

### 进阶问题

**Q：向量检索 + 关键词检索（BM25）混合检索有什么优势？**
> - **向量检索**：擅长语义相似（"汽车" 能匹配 "轿车"），但对精确词匹配弱
> - **BM25**：擅长精确词匹配（专有名词、代码、型号），但无法理解语义
> - **混合检索**：两路结果用 RRF（Reciprocal Rank Fusion）融合，取长补短，召回率更高

**Q：重排序（Reranking）是什么？为什么需要？**
> 向量检索的 Top-K 结果按向量相似度排序，但相似度高不等于对回答最有帮助。Reranker（如 Cross-Encoder）对每个检索结果和问题做精细的相关性打分，重新排序后取 Top-N 注入 Prompt。代价是计算量更大，通常只对 Top-K 做重排。

**Q：RAG 和 Fine-tuning 怎么选？**
> | 场景 | 选择 |
> |------|------|
> | 知识频繁更新 | RAG（更新索引即可，不需要重新训练） |
> | 私有知识库 | RAG（不需要把私有数据训练进模型） |
> | 改变模型行为/风格 | Fine-tuning |
> | 特定领域专业能力 | Fine-tuning（或两者结合） |
> | 快速上线 | RAG（无需训练） |

**Q：HyDE（Hypothetical Document Embeddings）是什么？**
> 用户问题直接向量化后检索效果有时不好（问题和答案的向量空间分布不同）。HyDE 的思路：先让 LLM 根据问题生成一个假设性的答案文档，用这个假设答案的向量去检索，因为假设答案和真实文档在向量空间更接近，召回率更高。

**Q：RAG 中如何处理多跳问题（Multi-hop QA）？**
> 多跳问题需要多个文档的信息组合才能回答（如"A 的老板的公司在哪里"）。处理方式：
> 1. **迭代检索**：第一次检索后，用中间结果生成新查询，再次检索
> 2. **子问题分解**：把复杂问题分解为多个子问题，分别检索后汇总
> 3. **知识图谱辅助**：结合结构化知识图谱做多跳推理
