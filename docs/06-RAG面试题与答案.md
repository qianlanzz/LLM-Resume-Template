# RAG 面试题与答案

> 来源：[小林面试笔记：RAG 面试题介绍](https://xiaolinnote.com/ai/rag/rag_info.html)
>
> 本文根据网页中的 20 道题重新归纳，答案经过压缩、校正并结合当前简历调整，适合面试口述。涉及项目数据量、延迟、召回率等指标时，只能使用真实数据，不要照搬示例数字。

## 一、基础概念

### 1. 什么是 RAG？完整的 RAG 系统是怎么工作的？

**面试回答：**

RAG 全称是 Retrieval-Augmented Generation，也就是检索增强生成。它不会修改大模型参数，而是在生成答案前，从外部知识库检索与问题相关的内容，再把检索结果和用户问题一起交给大模型，让模型基于这些资料回答。

完整流程分为离线和在线两个阶段。离线阶段负责加载 PDF、Word、网页等文档，完成清洗、切分、Embedding，并把文本、向量和 Metadata 写入索引。在线阶段先处理用户 Query，再进行向量检索或混合检索，通过 Rerank 重新排序，最后将高相关片段拼接进 Prompt，由大模型生成带来源的答案。

**核心流程：**

```text
离线：文档加载 → 清洗解析 → Chunking → Embedding → 写入索引
在线：Query 处理 → Query Embedding → 多路召回 → Rerank → Prompt → LLM 生成
```

**核心价值：**

- 接入私有知识和最新知识；
- 知识更新不需要重新训练模型；
- 回答可以引用来源、便于追溯；
- 相比直接塞入全部文档，可以降低上下文成本。

### 2. RAG 主要解决大模型的哪些问题？

**面试回答：**

RAG 主要解决知识时效性、私有知识缺失和回答缺少依据的问题。大模型训练完成后，参数中的知识基本固定，无法自动了解最新信息，也无法知道企业内部文档。RAG 把知识放在外部知识库中，在用户提问时实时检索，因此可以低成本更新知识，并让回答建立在可追溯的资料上。

RAG 还能降低幻觉，但不能彻底消除幻觉。如果检索没有召回正确内容，或者模型没有遵循检索上下文，最终仍然可能生成错误答案。

### 3. RAG 和微调有什么区别？如何选型？

**面试回答：**

RAG 和微调解决的问题不完全相同。微调会更新模型参数，更适合改变模型的输出风格、格式、行为模式，或者增强某类任务能力；RAG 不修改模型参数，而是在推理时注入外部知识，更适合知识频繁变化、需要引用来源以及企业私有知识问答的场景。

知识库问答通常优先选择 RAG，因为更新成本低、可解释性更强。需要让模型稳定遵循行业表达方式、输出特定格式或掌握特定任务模式时，可以考虑微调。两者也可以组合使用，用微调解决“怎么回答”，用 RAG 解决“回答依据是什么”。

| 对比项 | RAG | 微调 |
|---|---|---|
| 是否修改参数 | 否 | 是 |
| 知识更新 | 更新知识库即可 | 通常需要重新训练 |
| 来源追溯 | 容易实现 | 较难 |
| 主要用途 | 外部知识注入 | 风格、格式、任务能力 |
| 主要问题 | 检索质量决定上限 | 成本高、知识更新慢 |

## 二、索引构建

### 4. RAG 中的文档怎么存？Chunk 应该切多大？

**面试回答：**

文档通常先被切成多个 Chunk，每个 Chunk 分别生成向量，并保存原始文本和 Metadata。向量负责相似度检索，原始文本负责提供给大模型阅读，Metadata 保存文档 ID、文件名、标题、页码、更新时间和权限等信息，用于过滤、更新和来源追溯。

Chunk 大小没有固定答案，500～1000 Token 可以作为普通文本的实验起点，但最终要根据文档结构和业务评测确定。Chunk 太大容易包含过多无关内容，降低检索精度；Chunk 太小又容易丢失语义和上下文。

常见切分策略包括：

- 固定长度加 Overlap；
- 按标题、段落、句子等语义边界切分；
- 代码按类或函数切分，表格和图片单独处理；
- Parent-Child Chunking，即小块负责检索，大块负责返回上下文。

### 5. 如何避免文档切分破坏语义？

**面试回答：**

可以从“切分时保持完整”和“检索后补充上下文”两个方向处理。切分时尽量按照标题、段落和句子边界切，并保留一定 Overlap，避免一段完整语义被截断。检索后可以使用句子窗口，把命中片段前后的内容一起返回，也可以使用父子切分，用小 Chunk 精确命中，再返回对应的大 Chunk。

对高质量场景，还可以使用 Contextual Retrieval，在生成向量前为每个 Chunk 补充所属文档、章节和主题等背景信息，减少孤立片段缺少上下文的问题。

**常见组合：**

```text
结构化切分 + 适量 Overlap + Parent-Child + Rerank
```

### 6. Embedding 是什么？如何选择和评估 Embedding 模型？

**面试回答：**

Embedding 是把文本转换成稠密向量的过程，核心特性是语义相近的文本在向量空间中距离更近。建库时对文档 Chunk 生成向量，查询时对用户问题生成向量，再通过余弦相似度、内积等方式寻找相关片段。

选型时主要看业务语言和领域、最大输入长度、向量维度、推理延迟、部署成本、许可证以及是否支持 Query 和 Document 的不同指令格式。通用排行榜只能用于初筛，最终要在自己的业务数据上构造 Query—相关文档测试集，通过 Recall@K、Hit@K、MRR、NDCG 和延迟进行比较。

**结合项目：**

模型资源检索中使用了 Qwen3-Embedding，将模型名称、分类、描述、关联数据集和版本信息组合成检索文档，再通过 FAISS 完成语义检索。面试时需要重点说明模型为什么适合中文场景，以及最终应通过业务测试集而不是只看排行榜完成选型。

### 7. 常见的 Embedding 算法有哪些？

**面试回答：**

Embedding 技术可以大致理解为三代。Word2Vec、GloVe、FastText 属于静态词向量，同一个词在不同上下文中向量不变，因此难以处理多义词。ELMo、BERT 可以生成上下文相关表示，同一个词在不同句子中表示不同，但原始 BERT 并不是专门为句子相似度检索训练的。

SBERT、SimCSE、BGE、E5、Qwen3-Embedding 等模型通常采用双塔或对比学习思路，可以分别编码 Query 和 Document，提前计算并保存文档向量，查询时只需要计算一次 Query 向量，因此更适合大规模语义检索。

需要区分两种结构：

- Bi-Encoder：Query 和 Document 分别编码，速度快，适合召回；
- Cross-Encoder：Query 和 Document 拼接后联合编码，精度高但速度慢，适合 Rerank。

### 8. 什么是向量数据库？如何进行选型？

**面试回答：**

向量数据库是针对高维向量存储、近似最近邻搜索和 Metadata 过滤优化的系统。普通 B-tree 索引不适合高维相似度检索，因此向量系统通常使用 HNSW、IVF 等 ANN 索引，在检索精度、内存和延迟之间做取舍。

选型时主要考虑数据规模、并发量、更新频率、Metadata 过滤、混合检索、持久化、分布式能力和运维成本。FAISS 更准确地说是向量检索库，适合本机和可控规模场景，但数据库能力、权限、持久化和分布式能力需要自行补充。已有 PostgreSQL 可以考虑 pgvector；需要关键词与向量混合检索可以考虑 Elasticsearch；向量规模和并发较大时可以考虑 Milvus、Qdrant 等系统。

**常见索引：**

- Flat：精确检索，召回率高，但计算量大；
- IVF：先聚类再搜索部分倒排桶，速度快但需要训练和调参；
- HNSW：基于多层图搜索，查询性能较好，但内存占用较高。

### 9. 介绍一下项目中的向量检索方案、数据规模和性能瓶颈。

**适合当前简历的回答：**

我在模型资源管理平台中使用的是 Qwen3-Embedding 和 FAISS。先把模型名称、分类、描述、关联数据集和版本说明组织成统一检索文档，再生成向量写入 FAISS。用户输入自然语言任务描述后，系统生成 Query 向量，召回相似模型资源，并根据模型 ID 查询完整业务信息。

选择 FAISS 主要是因为当时数据规模可控、部署简单，而且检索服务可以独立维护。它的局限是本身不负责完整的数据库能力，Metadata 过滤、持久化、增量更新和权限控制需要业务层配合。如果数据量和并发继续增长，我会根据实际情况评估 HNSW、IVF，或者迁移到 Elasticsearch、Milvus 等服务化方案。

> 面试前需要补充真实信息：向量数量、向量维度、索引类型、Top-K、平均/P95 延迟、是否做过压测。没有正式测试的数据要明确说明，不要虚构。

## 三、在线检索与优化

### 10. 用户输入一个问题后，RAG 在线流程是什么？

**面试回答：**

用户问题进入系统后，通常先结合对话历史进行 Query 改写，消除“这个方案”“刚才那份文档”之类的指代。然后使用与建库阶段相同的 Embedding 模型生成 Query 向量，通过向量检索、BM25 或多路召回获取候选片段。

候选结果经过融合、去重和 Rerank 后，选择少量高相关片段，并在 Token 预算内拼接成 Prompt。Prompt 会要求模型基于资料回答、缺少依据时拒答，并保留文档 ID、页码等引用信息。最后由大模型生成答案，系统记录检索结果、引用来源、延迟和用户反馈，供后续评估优化。

### 11. 向量检索和关键词检索有什么区别？

**面试回答：**

BM25 等关键词检索主要依赖词频和逆文档频率，擅长产品型号、专有名词、数字和错误码等精确匹配，但不容易处理同义表达。向量检索根据 Embedding 的语义距离匹配，可以找出“iPhone 怎么截屏”和“苹果手机截图方法”这类表达不同但含义接近的内容，但对编号和精确关键词可能不够敏感。

两者通常不是替代关系。生产 RAG 可以同时使用 BM25 和向量检索，再通过 RRF 或加权分数融合候选结果，兼顾精确匹配和语义召回。

### 12. Query Rewrite 的目的是什么？有哪些方法？

**面试回答：**

Query Rewrite 的目标是把用户的口语化、模糊或依赖上下文的问题，改造成更适合检索的独立查询。比如用户问“刚才那个方案有什么风险”，系统需要结合历史对话补全具体方案，否则知识库无法理解“那个方案”指什么。

常见方法包括直接改写、补充关键词、多 Query 扩展、HyDE 和 Step-back Prompting。直接改写用于补全指代和规范表达；多 Query 从不同角度生成多个查询，提高覆盖率；HyDE 先生成一个假设答案，再用假设答案的向量检索；Step-back 将过于具体的问题抽象成更高层问题，用于召回背景知识。

Query Rewrite 也可能错误改变用户原意，因此需要保留原始 Query，并通过离线评测判断是否真的提升召回效果。

### 13. 什么是多路召回？具体怎么实现？

**面试回答：**

多路召回是并行使用多种检索方式获取候选内容，再进行融合和排序。常见组合是 Dense Retrieval 负责语义召回，BM25 负责关键词召回，再配合 Metadata 过滤和多 Query 扩展补充不同表述。

不同检索器的分数范围不一致，不能直接相加。可以先做分数归一化后加权，也可以使用 RRF，根据文档在各路结果中的排名计算融合分数：

\[
RRF(d)=\sum_i\frac{1}{k+rank_i(d)}
\]

融合后先去重，再使用 Cross-Encoder Reranker 精排，最终选择 Top-N 片段进入 Prompt。

### 14. RAG 检索效果不好时，可以从哪些方面优化？

**面试回答：**

我会按照索引、查询、召回和重排序四层排查，而不是一开始就更换大模型。索引层检查文档解析质量、Chunk 大小、Overlap、Metadata 和 Embedding；查询层检查指代消解、Query Rewrite、HyDE 和多 Query；召回层检查 Top-K、相似度算法、Metadata 过滤以及 BM25 与向量混合召回；重排序层检查 Reranker、去重和最终上下文预算。

实际优化前应该先建立评测集，区分问题是“正确文档没有被召回”，还是“已经召回但排序靠后”，或者“上下文正确但模型生成错误”。不同问题对应不同优化手段。

**典型组合：**

```text
结构化/父子切分
+ Query Rewrite
+ BM25 与向量多路召回
+ RRF 融合
+ Cross-Encoder Rerank
```

### 15. 了解哪些更复杂的 RAG 范式？

**面试回答：**

Naive RAG 是固定的检索加生成流程；Advanced RAG 会增加 Query Rewrite、混合检索、Rerank 和上下文压缩；Modular RAG 则把查询、检索、路由、校验等能力模块化，根据任务动态组合。

Self-RAG 让模型判断当前问题是否需要检索，并对检索结果和生成答案进行自我评估。CRAG 会评估检索质量，如果内部知识库质量不足，可以改写查询或使用其他数据源补充。GraphRAG 使用实体关系、社区发现和层次摘要，适合全局总结和跨文档关系问题。Agentic RAG 让 Agent 根据中间结果多轮规划、调用不同检索器并动态调整检索策略。

高级范式会提升复杂问题的处理能力，但也会增加延迟、成本和系统不可控性，因此应该根据评测结果使用，而不是为了复杂而复杂。

### 16. 哪些场景适合用图数据库增强向量检索？

**面试回答：**

当问题的答案不在单个文本片段中，而需要沿多个实体关系进行多跳推理时，可以考虑图数据库。例如企业股权关系、供应链溯源、医疗知识图谱、代码依赖和金融风险传播等场景。

向量检索擅长找到语义相关的片段，但不会天然维护实体之间的精确关系。比较常见的组合是先通过向量检索定位相关实体或文档，再通过图数据库沿关系边扩展邻居，最后把文本证据和图关系一起交给大模型。

如果场景只是普通文档问答，不需要实体关系和多跳推理，引入图数据库会增加实体抽取、关系维护和查询复杂度，不一定值得。

## 四、生产落地与评估

### 17. 如何降低 RAG 系统中的幻觉？

**面试回答：**

RAG 中的幻觉通常有两个来源：检索层没有提供正确资料，或者生成层没有严格依据资料回答。因此需要同时治理检索和生成，而不是只在 Prompt 中加一句“不要编造”。

检索层可以通过混合召回、Rerank、相关性阈值和空结果检测保证上下文质量，低于阈值时直接拒答。生成层通过 Prompt 约束模型只根据资料回答，并要求每条关键结论带引用。生成后还可以做引用核验或事实一致性检查，确认答案中的结论能够在原始 Chunk 中找到依据。

还要防止检索内容中的提示注入影响系统指令，因此外部文档只能作为资料，不能当成可执行指令。

### 18. 如何量化 RAG 的效果？

**面试回答：**

RAG 评估需要分成检索层、生成层和线上业务层。检索层主要判断相关文档是否召回以及排序是否合理，可以使用 Hit@K、Recall@K、MRR 和 NDCG。生成层关注答案是否忠于上下文、是否回答了问题以及上下文是否充分，可以使用 Faithfulness、Answer Relevancy、Context Precision、Context Recall，也可以结合人工评审和 LLM-as-a-Judge。

线上还需要观察点踩率、追问率、无答案率、转人工率、任务完成率、P95 延迟和调用成本。离线指标用于定位技术问题，线上指标才用于判断系统是否真正产生业务价值。

**定位思路：**

- Recall@K 低：优先排查解析、Chunking、Embedding 和 Query；
- 召回正确但排序差：优化融合和 Rerank；
- 上下文正确但答案错误：优化 Prompt、模型和事实校验；
- 技术指标正常但用户不满意：检查回答风格、业务流程和评测集代表性。

### 19. RAG 知识库如何实现动态更新？

**面试回答：**

动态更新的关键是稳定标识、变更检测、增量索引和一致性控制。可以为每个文档保存 documentId、contentHash 和版本号，通过定时轮询、Webhook、CDC 或消息队列检测新增、修改和删除事件。

文档修改后，通常根据 documentId 删除旧 Chunk，再重新解析、切分、生成向量并写入新版本。Chunk ID 可以由 documentId、版本和序号组成，保证更新和删除可追踪。写入过程需要保证幂等，避免消息重试产生重复向量。

生产环境还可以采用新旧索引并存或 Alias 切换：先构建并验证新版本索引，确认成功后再切换流量，避免更新过程中出现部分旧数据、部分新数据的不一致状态。

### 20. RAG 实际落地最难的地方是什么？

**面试回答：**

我认为最难的不是把 Demo 跑起来，而是保证输入数据质量、检索效果和评估闭环。原始 PDF 可能包含扫描图片、表格、多栏排版和错误 OCR，如果解析阶段已经丢失结构，后面的 Embedding 和大模型都无法补救。

检索效果调优也比较复杂，因为 Chunking、Embedding、Query、召回和 Rerank 都会影响最终答案。如果没有分层评测，很难判断问题到底出现在哪个环节。生产环境还要处理权限、动态更新、延迟、成本和监控，这些通常比调用一次模型接口更困难。

结合教辅录题系统，我处理过 PDF 结构复杂、题目页和答案页分离的问题。解决方式不是直接把全文交给模型，而是先用 MinerU 保留块级坐标和目录结构，再结合章节标题、题号和大模型完成题答配对。这段经历可以用来说明 AI 系统的数据预处理质量往往决定后续效果上限。

## 五、结合当前简历最可能被追问的问题
