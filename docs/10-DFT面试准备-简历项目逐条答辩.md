### Bullet 2

> **原文**：基于 Qwen3-Embedding-0.6B + FAISS 实现语义检索；将模型名称、分类、描述、关联数据集和版本说明拼成检索文档，支持用自然语言任务描述召回候选模型。

**一句话复述**：用户输入一句自然语言需求（比如"找图像目标检测的模型"），系统返回语义相关的模型列表。用 0.6B 的向量模型把模型元数据编码成向量，用 FAISS 做近邻检索。

**必答题链**

**Q1：为什么要用语义检索，不用关键字检索？**
> 因为用户经常"只记得任务描述，不记得模型名"。关键字检索要求用户猜中词——用户说"能识别图片里是什么东西的模型"，关键字匹配不到"图像分类"这个词。语义检索把 query 和文档都映射到同一个向量空间，靠**语义距离**而不是字面匹配召回，能处理同义、换述、跨语言表达。

**Q2：Embedding 模型是怎么工作的？**
> 它是一个 Transformer 编码器，把一段文本映射成一个固定维度的稠密向量。训练目标是让语义相近的文本向量距离近、无关的远（对比学习，in-batch negatives 之类的）。Qwen3-Embedding-0.6B 输出的是 1024 维向量（不同配置可能不同，按实际说），0.6B 参数是它的规模——选它是在效果和推理成本之间做的折中：部署到单机 GPU 就能跑，延迟可接受。

**⚠️ 必须核实的数字**：Qwen3-Embedding-0.6B 的输出维度请按实际配置回答（常见 1024）。面试官如果追问维度而你答错，会显得没真做过。**去确认你线上配的维度。**

**Q3：为什么用 FAISS，不用别的向量库（Milvus / pgvector / ES）？**
> 三个原因：
> 1. **数据量小**：模型资源是几万条量级，不需要分布式向量库。FAISS 单机内存索引足够，而且延迟极低。
> 2. **运维成本**：项目是内网环境、单体部署，多引入一个中间件就是多一份运维和故障面。FAISS 是库不是服务，进程内调用。
> 3. **可控性**：索引文件是我们自己的文件，可以做快照、做版本，方便回滚和迁移。

*对比句加分*：如果数据涨到千万级或者需要多租户隔离，我会换成 Milvus 或者带 HNSW 的 pgvector，那时候 FAISS 的单机内存索引在更新和并发上就吃力了。

**Q4：FAISS 有哪些索引类型？你为什么选那个？**

这是高频八股，必须背：

| 索引 | 原理 | 特点 |
|---|---|---|
| **IndexFlatL2 / IndexFlatIP** | 暴力穷举，精确最近邻 | 100% 召回，O(N) 每次查询，几万条以内完全够用 |
| **IndexIVFFlat** | 先聚类（k-means）分桶，查询时只搜最近的 nprobe 个桶 | 快，但**有召回损失**，需要训练 |
| **IndexIVFPQ** | IVF + 乘积量化（PQ）压缩向量 | 内存大幅降低，精度进一步损失，适合亿级 |
| **IndexHNSWFlat** | 分层可导航小世界图 | 高召回 + 高速度，内存开销大，构建慢 |
| **IndexLSH** | 局部敏感哈希 | 快，但召回一般 |

> 我选的是 **Flat（内积或 L2）**，因为数据量在几万条，暴力检索的单次耗时是毫秒级，完全可接受，而且**精确、无召回损失、无需训练**——省掉了聚类训练和参数调优的复杂度。等到数据量上升，第一选择是 **IVFFlat**（保留原始向量，支持按需重排），配合 `nprobe` 调召回率；再往上才考虑 PQ 压缩。

**Q5：FAISS 的 L2 和 IP 有什么区别？怎么选？**
> L2 是欧氏距离，越小越相似；IP 是内积，越大越相似。**如果向量做了 L2 归一化，两者等价**（因为 `||a-b||² = ||a||² + ||b||² - 2a·b`，归一化后前两项都是常数）。实践中 embedding 通常归一化后用 IP（等价余弦相似度），因为内积计算更快（没有开方和减法）。我这边用的是归一化 + 内积。

**Q6：你说的"拼成检索文档"具体怎么拼？为什么这么拼？**

这是你简历里的关键词，一定要能展开：

> 把一条模型记录的多个字段拼成一段结构化文本再编码。大概是：
> ```
> 模型名称：目标检测-YOLOv8改进版
> 分类：计算机视觉 / 目标检测
> 描述：面向遥感图像的舰船目标检测，支持多尺度...
> 关联数据集：遥感舰船数据集 v2（1.2万张）
> 版本说明：v1.3 提升小目标召回
> ```
> 这么做的原因有三点：
> 1. **单字段编码会丢上下文**。只编码"描述"字段，用户搜索时会用到分类词或数据集名，召不到。
> 2. **字段名本身就是语义信号**。"分类：目标检测"比光写"目标检测"信息更明确，因为模型见过大量带字段名的文本。
> 3. **便于加权**。如果需要，可以对不同字段做重复拼接（比如名称拼两次）来提升权重，这比改模型简单得多。
>
> 缺点是长文档会被截断（embedding 模型有 token 上限，通常 512 或 8192），所以我们控制了拼接长度，超长描述先做摘要。**这个截断问题是个诚实的追问点，要说出来。**

**Q7：模型更新了，索引怎么办？**
> 增量更新：元数据变更后触发 upsert/delete。写入侧先在 staging 目录构建新索引，构建完用原子操作（`os.replace`）替换线上索引文件；查询侧持有只读快照，正在服务的请求用旧快照，新请求用新快照。这样避免**半写入状态**被读到。

*这句"staging + os.replace + 只读快照"是你简历里真实写过的（见 resume-zhangzhe-interview.md 第 27 行），能讲。*

**Q8：为什么不直接上 RAG 让大模型答？**
> 场景不同。这里是**资源检索**不是**问答**——用户要的是"给我一个候选列表，我自己挑"，不是"你给我一段总结"。列表可点可进详情页，可追溯；大模型生成的答案反而不可信、不可操作。我们只把大模型用在候选排序和推荐解释上。

### Bullet 3

> **原文**：实现模型资源推荐模块，将用户历史行为、资源类型偏好和近期热度合并排序；对高频推荐结果做用户级 Redis 缓存，减少重复计算和接口抖动。

**一句话复述**：给用户推荐可能感兴趣的模型资源，用三类信号加权排序，结果按用户缓存到 Redis。

**必答题链**

**Q1：三类信号怎么合并？为什么这么设计？**

> 用加权评分：
> ```
> score = w1 × 行为分 + w2 × 偏好分 + w3 × 热度分
> ```
> - **行为分**：用户历史下载/收藏/部署过的资源，做同类型召回（item-based）。反映"个人历史"。
> - **偏好分**：用户对各资源类型（模型/算法/数据集/镜像）的点击占比。反映"类型倾向"。
> - **热度分**：近期被访问/下载的次数，做**时间衰减**（越近的访问权重越高）。
>
> 三个信号互补：行为分是"你自己的历史"，偏好分是"你这类人的倾向"，热度分是"大家都在看什么"。只有行为分会导致推荐越来越窄（信息茧房）；加热度分能出新东西；加偏好分能解决新用户冷启。

**Q2：时间衰减怎么算？**
> 常用 `score = Σ exp(-λ × Δt)` 或 `score = count / (t - t0 + c)^α`。前者是指数衰减，简单好算。λ 决定"多快忘掉旧行为"，需要根据业务节奏调——比如一周调一次就取半衰期 7 天左右。

**Q3：为什么用 Redis 缓存？缓存什么粒度？**
> 推荐计算要遍历用户行为和候选资源列表，是 O(用户数 × 候选数) 的活，每次请求都算会拖慢接口。
> 缓存粒度是**用户级**（key = 用户 ID + 场景），存排好序的 top-N 结果。
> 因为推荐是"个人化"的，缓存全局结果没意义；但同一个用户短时间内重复刷同一个页面很常见，用户级缓存命中率就很高。

**Q4：缓存怎么失效？（必问）**
> 三个触发点：
> 1. **TTL 到期**：设置合理过期时间，兜底防止脏数据长期存在。
> 2. **主动失效**：用户产生新行为（下载/收藏）、或资源元数据变更时，主动删除该用户的缓存 key，下次请求重建。
> 3. **热度自然过期**：因为打分里带时间衰减，TTL 到期重建后热度分自动更新，不需要专门处理。
>
> 关键取舍：**不能只在元数据变更时失效所有用户缓存**，那会导致缓存雪崩，写入侧被打爆。所以我们只失效受影响的用户，或者干脆靠短 TTL 兜底。

**Q5：缓存穿透、击穿、雪崩怎么处理？**
> - **穿透**：查不存在的数据。加空值缓存（短 TTL）或者布隆过滤器。
> - **击穿**：热点 key 过期瞬间大量请求打到后端。加互斥锁（只让一个请求重建）或者逻辑过期（不删 key，异步刷新）。
> - **雪崩**：大量 key 同时过期。TTL 加随机抖动。
>
> 我们这边实际用到了 TTL 抖动和单请求重建（Redis 锁），因为推荐 key 是按用户分散的，穿透和雪崩风险本身较小。

**Q6：为什么不用协同过滤 / 深度学习推荐模型？**
> 数据量不够。协同过滤在用户数少、行为稀疏时会严重退化（冷启 + 稀疏矩阵）。规则加权在这类**内部平台**场景可解释性好得多——用户/运营能看懂"为什么推荐这个"，也方便按业务反馈调权重。等行为数据积累到一定规模，可以考虑 item2vec 或双塔召回模型。

### Bullet 4

> **原文**：补充系统运行监控和智能分析能力，基于 psutil 采集 CPU、内存、磁盘、网络等指标，用 DBSCAN 标出异常时段，并用线性回归给出 7 天资源趋势，辅助运维提前发现容量风险。

**一句话复述**：采集服务器指标，用聚类找异常时间段，用回归预测未来趋势，帮运维提前知道资源快不够用了。

**必答题链**

**Q1：psutil 采什么？采多少频率？怎么存？**
> 采 CPU（总体 + 每核）、内存（已用/可用/swap）、磁盘（使用率 + 读写 IO）、网络（收发字节、连接数）。频率通常 10–60 秒一次，太密会有采集开销和存储压力。
> 存储上：原始数据量不大，可以直接落库（时序场景可以按时间分表）。**要说明采样频率和数据保留策略**——这是面试官判断你有没有真上过生产的关键细节。

**Q2：DBSCAN 是什么？为什么用它做异常检测？**

必背：

> DBSCAN（Density-Based Spatial Clustering of Applications with Noise）是基于密度的聚类算法。两个参数：`eps`（邻域半径）和 `minPts`（成为核心点所需的最少邻居数）。点的分类：
> - **核心点**：eps 邻域内的点数 ≥ minPts
> - **边界点**：不是核心点，但落在某个核心点的邻域内
> - **噪声点**：既不是核心点也不是边界点
>
> 优点是：**不需要预先指定簇数量**（对比 k-means 必须给 k）、**能发现任意形状的簇**、**天然能识别噪声点（离群点）**。这正好符合异常检测的需求——异常时段就是"密度低、离正常簇远"的那些时间点。

**Q3：为什么不用 k-means / 孤立森林 / 3-sigma？**

对比表（被问到的概率很高）：

| 方法 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| **3-sigma / 阈值** | 极简单、可解释 | 假设正态分布；多指标耦合场景下误报多 | 单指标、稳定基线 |
| **k-means** | 快、简单 | 必须指定 k；假设球形等大小簇；对离群点敏感（均值被拉偏） | 已知簇数的分组 |
| **DBSCAN** | 免 k、任意形状、自带噪声识别 | 对 eps/minPts 敏感；高维效果差；密度不均时表现差 | **密度可分的异常检测** |
| **孤立森林（IForest）** | 无监督、高维有效、O(n log n) | 需要足够样本；可解释性较弱 | 多维异常检测 |
| **LOF** | 局部密度，能发现局部异常 | 计算量大 | 局部离群 |
| **时间序列专用（STL / Prophet / ARIMA 残差）** | 考虑了周期性和趋势 | 需要足够历史数据建模 | 有明显周期性的指标 |

> 我选 DBSCAN 的理由：监控数据在时序上有明显的"常态密度区"（比如 CPU 20–40% 是常态）和"异常稀疏区"，DBSCAN 不用预设异常有几类，天然把稀疏的点判为噪声，不需要标注数据训练。**如果指标维度很高（比如同时看 20 个指标），DBSCAN 的距离度量会失效（维度灾难），那时候我会换孤立森林或者先做 PCA 降维。**

**Q4：DBSCAN 的 eps 和 minPts 怎么定？**
> 经验法：先画 **k-距离图（k-distance plot）**——对每个点算它到第 k 近邻的距离，排序后画曲线，取拐点（elbow）作为 eps。minPts 一般取 `维度 + 1` 或 `2 × 维度`，也可以用 `ln(n)` 做下界估计。
> 实际工程上我会**做参数扫描 + 人工复核**：跑几组参数，把标出的异常时段交给人看，选误报最少的。因为这本质是个业务问题——异常检测的目标不是数学最优，而是让运维愿意看告警。

**Q5：为什么要做"异常时段"而不是"异常点"？**
> 因为监控指标有噪声。单点尖峰（比如一次 GC、一次备份任务）不是真异常，运维看了会疲劳。DBSCAN 按密度聚类，**天然把相邻的异常点聚成一个时段**，输出"14:00–14:15 CPU 持续异常"这种结论，比"14:03 CPU=95%"有用得多。

**Q6：线性回归做 7 天趋势，怎么保证不太离谱？**

这是最容易被追问穿的一条，**必须诚实**：

> 线性回归在这里的作用是**趋势外推的粗略参考**，不是精确预测。
>
> 具体做法是：用过去 N 天（比如 30 天）的日粒度指标（比如磁盘使用率的日终值）拟合 `y = a×t + b`，然后外推 7 天，给出"按当前增速，第 7 天会达到 X%"。**同时给出 R² 作为拟合可信度**，R² 低的时候标记为"趋势不明显"。
>
> 局限我很清楚：
> 1. 线性模型抓不到周期性和突变（比如某天导入了一批数据，磁盘暴涨）。
> 2. 长期外推误差会累积。
> 3. 不同指标的增长模式不一样——磁盘接近线性，CPU 更接近平稳波动。
>
> 所以定位是**"容量预警的粗筛"**，输出给运维做参考，不作为自动扩容依据。如果要做更准，会换成分位数回归（给区间而不是点估计）、或者 Prophet 这类带周期的模型，并且对磁盘这类单调指标用更适合的方法。

**⚠️ 强烈建议**：如果面试官是资深的，他大概率会问「线性回归预测资源趋势合理吗」——这是**送分陷阱题**，考你知不知道自己的方法有局限。**主动说出局限**比嘴硬好一百倍。

**Q7：这一条和 DFT 有什么关系？**（如果面试官这么问）
> 本质上都是**从运行数据里发现异常、做趋势预警**。DFT 里对应的场景是测试良率监控、ATE fail log 的模式分析——比如某条扫描链的失败率突然上升，或者某个测试项的 fail 集中出现，需要从大量测试数据里找出系统性模式。方法论是一样的：采集 → 清洗 → 找离群 → 给结论。

## 2. 九方智投｜JF-AIX 企业级 Agent 数字员工平台｜2026.05–2026.08

### Bullet 1：Agent Runtime 与端云协同

> **原文**：参与构建 Electron + Vue 3 端侧执行域与 NestJS 云侧控制面，基于 Pi Agent SDK 接管自定义 Agent Loop，完善 Tool 循环熔断、参数校验、输出截断续写、Abort 中断及流式事件分发机制，将模型推理、Tool/Skill 执行、人工确认与结果持久化串联为可观测、可中断、可恢复的执行闭环。

**一句话复述**：我负责 Agent 的执行引擎——模型要调工具、工具可能失败或卡死、输出可能被截断、用户可能中途取消，我保证这整套流程能被观测、能中断、能恢复。

**必答题链**

**Q1：什么是 Agent Loop？为什么不用 SDK 自带的，要自己接管？**
> Agent Loop 就是"模型输出 → 解析出工具调用 → 执行工具 → 把结果回灌给模型 → 再让模型决策"的循环，直到模型不再请求工具、输出最终答案。
> SDK 自带的 loop 是通用实现，缺我们要的能力：需要循环熔断上限、需要细粒度的参数校验、需要处理输出截断续写、需要支持人工确认节点（human-in-the-loop）、需要把每一步事件流式推给前端并落库。所以我们在 SDK 之上接管了 loop 的主体控制权，SDK 只提供模型调用和工具协议适配。

**Q2：「Tool 循环熔断」具体防什么？怎么实现的？**
> 防三种死循环：
> - **模型反复调同一个工具**（比如反复调用搜索但拿不到结果），需要检测重复调用并在超过阈值时打断。
> - **工具之间互相触发**导致无限链式调用。
> - **单次任务总步数失控**，烧 token 烧钱。
>
> 实现上是**多级熔断**：单工具在单轮内重复调用次数上限、单个任务总步数上限、总 token 预算上限、总执行时长上限。任一触发就终止循环，把已有结果和终止原因返回给用户。
> 关键设计是**熔断要有可解释的终止原因**——不能静悄悄断掉，用户会以为系统坏了。我们会返回"因重复调用相同工具已达 N 次而中止，以下是已获得的中间结果"。

**Q3：「参数校验」校验什么？用 Schema 还是手写？**
> 校验模型生成的工具参数：类型、必填、枚举范围、格式（路径、URL）。
> 用 **JSON Schema** 定义工具参数，校验器统一校验。校验失败**不直接抛错终止**，而是把错误信息作为工具结果回灌给模型，让它自己修正重试——这是 Agent 场景和普通 API 的关键区别：**错误是给模型的输入，不是给用户的异常**。只有连续修正失败才终止。
> 另外还有**安全性校验**：路径越界（不能访问沙盒外的文件）、危险命令、超大输出截断。

**Q4：「输出截断续写」是什么问题？**
> 模型有最大输出 token 限制。当它要生成一个很长的结果（比如一大段代码、一份长文档）时，输出会在中途被截断，JSON 结构可能都不完整。
> 处理方式是：检测结束原因（`finish_reason == "length"`）→ 把已生成内容作为前缀，追加指令让模型从截断处继续 → 拼接 → 循环直到正常结束或达到上限。对 JSON 类输出，还需要在拼接后做结构完整性校验，必要时修复（补齐括号）或要求模型重发。
> 陷阱是**重复内容**：续写时模型常把最后一段重说一遍，所以拼接前要做后缀-前缀去重。

**Q5：「Abort 中断」怎么做到「可中断」？中断后资源怎么回收？**
> 全链路传递 `AbortSignal`（AbortController）：前端点取消 → 通过流式通道发中断请求 → 服务端 AbortController.abort() → 正在进行的模型调用和工具执行都收到信号并退出（HTTP 请求取消、子进程 kill、文件句柄关闭）。
> 关键点：
> 1. **中断要落库**：会话状态标记为 `aborted`，已产生的消息保留，用户能看到"这次执行被取消了"。
> 2. **不产生半写入状态**：工具执行如果有副作用（写文件、调外部 API），要么做成幂等，要么用事务/临时文件 + 原子替换。
> 3. **要能恢复**：因为每步事件都持久化了，用户可以基于已有状态继续对话。

**Q6：「流式事件分发」为什么重要？**
> 因为 Agent 执行可能是几十秒到几分钟。如果等全部结束再返回，用户会以为卡死了。
> 流式分发把执行过程切成事件：`step_start`、`tool_call`、`tool_result`、`token`（增量文本）、`confirm_required`、`done`、`error`。前端按事件实时渲染，用户能看到"正在调用 XX 工具"。这同时也是**可观测性的基础**——事件流就是天然的审计日志。

**Q7：「人工确认」怎么实现的？**
> 某些高风险工具（删文件、发邮件、调支付）在执行前挂起：runtime 发出 `confirm_required` 事件并暂停循环，把待确认的调用挂到会话状态里；用户确认后，前端调用 resume 接口带上 confirmation token，runtime 从挂起点继续。这里的关键是**挂起状态必须持久化**，否则应用重启或换设备就丢了。

**Q8：「可恢复」靠什么保证？**
> 每步事件持久化 + 循环状态可重建。恢复时读回历史事件和消息，重建上下文（包括已执行的工具调用及结果），从断点继续。要防止**重复执行副作用工具**，所以每个工具调用要有唯一 ID 和幂等标记，恢复时先检查该调用是否已完成。

**Q9：这一条和 DFT 有什么可迁移的？**
> 三个点：
> 1. **大流程的状态机 + 断点续跑**：DFT 里的 ATPG、门级仿真、回归都是长流程，中断和续跑是刚需。
> 2. **可观测性**：Agent 的事件流和我给 DFT 做覆盖率/日志看板是同一个需求。
> 3. **幂等和去重**：重复跑 ATPG 浪费机时，和重复调模型浪费 token 是一回事。

### Bullet 2：会话级多模态文件记忆

> **原文**：面向会话内少量小型文档、图片及表格附件，设计"首轮原始内容注入 → 异步摘要与图片描述 → 后续摘要引用 → 精确信息按需回读"链路；通过 Renderer 会话状态、Electron 本机缓存与 Server Metadata 三级分层管理文件内容和引用，在不引入向量库及文档分块的情况下，实现文件跨轮持续使用和应用重启恢复；基于模型上下文容量动态分配多文件内容预算，并通过 `documentId + hash` 校验、原子写入及 Draft Session 迁移保障缓存一致性。

**一句话复述**：用户往对话里传文件，文件内容不能每轮都重发（太贵），但后面还得能用上——所以第一轮发原文，之后发摘要，需要细节时再按需回读。

**必答题链**

**Q1：为什么"不引入向量库和文档分块"？这是不是技术能力不足？**

**这是本条最容易被质疑的点，必须有一个强回答**：

> 这是一个**刻意的取舍**，不是做不到。
>
> 场景约束是：**会话内的少量小型文档**。典型是一个几页的 PDF、一张图、一个几十行的表格。在这个规模下：
> - 文档总共可能就 5–20 个片段，向量检索的召回质量优势体现不出来——**直接全塞进上下文反而更准**，因为不做分块就不会切断语义。
> - 引入向量库意味着：额外的服务依赖（内网部署、运维成本）、embedding 调用成本、分块策略调参、召回错漏导致的"幻觉引用"。这些成本在"少量小文件"场景下**收益为负**。
> - Electron 端侧应用尤其如此——我们不能假设用户机器上能跑一个向量数据库。
>
> 所以设计目标是"**在最小的架构代价下做到跨轮可用 + 重启可恢复**"。真正需要向量检索的是**跨会话长期记忆**（简历下一段），那个场景数据无限增长、相关性稀疏，必须用检索。**两个场景用两套方案，是因为它们的规模特性完全不同。**

**这句话把"为什么两边方案不一致"解释清楚了，是很强的加分点。**

**Q2：为什么要"首轮原始内容注入 → 后续摘要引用"？直接每轮都发原文不行吗？**
> 成本。多轮对话里，每轮的上下文都包含历史，如果原文有 8000 token，聊 10 轮就是 8 万 token 的重复输入（而且每轮还要再发一次），成本和延迟都不可接受。
> 分级策略：**首轮注入原文（保证第一次理解准确）→ 异步生成摘要和图片描述 → 后续轮次只带摘要 → 模型需要精确细节时通过工具按需回读原文片段**。这样把"贵但准"的原文注入限制在少数几次。

**Q3：「异步摘要」的时序怎么处理的？如果用户第二轮就问了，摘要还没生成完怎么办？**
> 三种兜底：
> 1. **同步优先**：如果摘要未就绪，本轮仍注入原文（退化为首轮策略），只是贵一点，但正确性不受影响。
> 2. **状态标记**：文件元数据里有 `summaryStatus`（pending / ready / failed），调度时按状态决定注入什么。
> 3. **失败降级**：摘要生成失败不影响主流程，永久回退到按需回读原文。
>
> 核心原则：**摘要只是优化，不是依赖**。这个原则要能说出来。

**Q4：三级分层（Renderer / Electron 本机缓存 / Server Metadata）各自管什么？为什么要分？**

| 层级 | 存什么 | 生命周期 | 为什么 |
|---|---|---|---|
| **Renderer 会话状态** | 当前会话的文件引用、注入预算、本轮已注入标记 | 页面会话 | 最快，避免每轮都走 IPC 和网络 |
| **Electron 本机缓存** | 文件正文、解析结果、图片描述（大块内容） | 应用生命周期，可清理 | 内容大，放本机省服务端存储和网络传输；应用重启后还能用 |
| **Server Metadata** | documentId、hash、文件名、摘要、状态、归属会话 | 持久 | 跨设备、跨重启的**权威记录**，也是校验和清理的依据 |

> 分层的理由：**内容大、生命周期短、可重建 → 放端侧；元数据小、需要权威和跨端 → 放服务端。** 这是典型的 cache-aside 分层思路。

**Q5：`documentId + hash` 校验具体防什么？**
> 防三种不一致：
> 1. **内容被篡改/替换**：同名文件内容变了，hash 不同，缓存失效重建。
> 2. **缓存与元数据不一致**：本机缓存的正文和 Server 记录的 hash 对不上，说明缓存脏了或版本错位，丢弃重取。
> 3. **重复上传去重**：同一个文件重复传，hash 相同可直接复用已有解析结果，省一次解析成本。

**Q6：「原子写入」怎么实现？为什么必须？**
> Electron/Node 里就是 **写临时文件 → `fsync` → `rename` 原子替换**。不能直接覆写目标文件，因为写入过程中崩溃/断电会留下半个文件，下次读到损坏内容。
> 这也是我在 FAISS 索引更新里用的同一招（staging + os.replace）——**同一个模式在两个地方复用**，这个一致性可以主动讲出来。

**Q7：「Draft Session 迁移」是什么问题？**
> 用户新建会话（draft，还没落库）时上传了文件，然后第一句话才真正创建会话。这时文件引用要从 draft 状态迁移到真实 session 上，否则文件就"丢了"。
> 做法：draft 阶段文件先挂在临时 ID 下，会话正式创建时执行一次原子迁移（更新归属 + 确认元数据），迁移完成后才返回可用状态。要处理迁移失败的回滚——否则会出现"会话建了但文件找不到"。

**Q8：「模型上下文容量动态分配预算」怎么算？**
> 先估算本轮可用预算：`模型上下文窗口 - 系统提示 - 历史对话 - 预留输出空间 - 安全余量`。然后按策略分配给多个附件：优先级排序（用户显式提到的 > 最近上传的 > 更早的）、单文件上限、总量上限。超预算的附件降级成摘要或只保留引用。
> 关键词是**动态**：不是固定"每个文件给 X token"，而是跟着本轮历史长度浮动。

**Q9：为什么不做文档分块 + 向量检索？（追问加强版）**
> 再说一次：**少量小文件场景下，分块本身就是损失。** 分块会切断表格的跨行关系、切断图片和它上下文的关联，检索时可能召回一个语义不完整的片段，模型据此回答反而更容易出错。在这个规模下，**精确注入优于模糊召回**。
> 如果场景变成"用户上传一本 500 页的文档"，那我第一件事就是上分块 + 检索，否则上下文塞不下——我们平台另一个项目（教辅录题）里处理教材 PDF 就是这个思路，300 多页的文档必须先切题、按题存，不能整本注入。

**这个回答把两个项目串起来了，非常有说服力。必须准备。**

### Bullet 3：跨会话长期记忆

> **原文**：设计与会话文件记忆相互隔离的用户长期记忆链路，每轮结束后异步提炼 `user`、`feedback`、`project`、`reference` 四类稳定事实，以 MySQL 持久化并通过 Elasticsearch 向量检索召回候选记忆，再由 LLM 结合当前任务进行相关性严选；按用户与 Agent 作用域注入 L6 动态上下文，减少无关记忆干扰，避免临时文件内容进入长期记忆导致事实污染。

**一句话复述**：跨对话记住用户的稳定偏好和项目背景，但只记"应该长期记住的东西"，靠向量检索 + 大模型严选控制注入量。

**必答题链**

**Q1：为什么标"四类"？这四类怎么来的？**
> 借鉴的是长期记忆的经典分类（类似 Anthropic 的 memory 工具分类）：`user`（用户是谁、偏好）、`feedback`（用户对输出的纠正和偏好反馈）、`project`（项目背景、目标、约束）、`reference`（外部参考资料指向）。
> 分类的目的有三个：
> 1. **写入时有结构**，提取 prompt 更聚焦，不容易乱记。
> 2. **召回时可加权**，比如当前任务明确提到项目名时优先召回 `project` 类。
> 3. **便于治理**：用户可以按类别查看和删除记忆，不同类型可以有不同的 TTL 和置信度策略。

**Q2：为什么要"与会话文件记忆相互隔离"？**
> 因为这个隔离是**防污染的关键**。文件内容是**任务级、临时**的；长期记忆是**跨任务、稳定**的。如果混在一起：
> - 用户传了一份临时参考文档，里面的内容被记成"用户偏好"，下次对话就会莫名其妙地按那个文档的风格回答。
> - 文件里的敏感/时效内容长期留在记忆里，是数据安全问题。
>
> 所以两条链路在数据模型、存储、生命周期上完全分开，只在**注入阶段**按作用域分别拼装。简历里那句"避免临时文件内容进入长期记忆导致事实污染"就是这个意思。

**Q3："L6 动态上下文"是什么？为什么叫 L6？**
> 是上下文分层的一个编号：常见做法是把系统上下文分层，比如 L1 系统人设、L2 全局规则、L3 工具说明、L4 会话摘要、L5 文件摘要、**L6 用户长期记忆**。编号本身因团队而异，重要的是**分层的原则**：越稳定的越靠前、越动态的越靠后、越容易被裁剪的越靠后。
> L6 的特点是**动态**——每次请求按当前任务检索出来的记忆子集，不是固定内容。放在最外层的好处是它最容易按预算裁剪，也最容易做 A/B 和可观测（每条记忆被召回/注入/使用都可以打点）。

⚠️ **如果面试官追问"L1–L5 具体是什么"**，而你说不出，会尴尬。**建议提前和团队/自己的实现对齐，或者回答时说明"分层编号是团队约定，核心是分层原则"**。

**Q4：提取是在"每轮结束后异步"做的，为什么异步？失败了怎么办？**
> 异步的原因：提炼要调一次 LLM，同步做会给每轮对话加几百毫秒到几秒的延迟，用户直接感知到。
> 失败处理：写进任务队列，有重试；连续失败就丢弃（**长期记忆的丢失是可接受的**，因为它只是优化，不影响当前任务正确性）。同时要有幂等键（会话 ID + 轮次）防重复写入。

**Q5：为什么用 Elasticsearch 做向量检索，而不是 MySQL 或 FAISS？**
> 因为我们已经用 ES 做日志/检索基础设施，ES 7+ 原生支持 `dense_vector` 字段和 kNN 检索（后续版本有 HNSW 加速），可以直接复用现有的集群和运维能力，不用再引入一个向量库。
> 对比：
> - **MySQL**：没有向量索引，只能把向量取出来自己暴力算，数据量大了不可行。
> - **FAISS**：是库不是服务，在多实例部署下索引同步和一致性麻烦。
> - **ES**：作为服务天然支持多实例，同时支持**向量 + 标量过滤**（比如只召回某个用户的记忆），这正是我们需要的。
>
> 如果需要更高性能的纯向量场景，会考虑 Milvus 或 pgvector。

**Q6：召回候选之后"Why 还要 LLM 严选"？不能直接按相似度取 top-K？**
> 因为**相似 ≠ 相关**。向量检索抓的是语义接近，但很多候选是"话题相近但和当前任务无关"的记忆——比如用户之前聊过 A 项目，现在聊 B 项目，A 的记忆语义上可能也接近（都是技术话题），但注入进去纯属干扰。
> LLM 严选的作用是**结合当前任务判断这条记忆是否真的有用**，并把选中的记忆压缩成一句可注入的话。这就是典型的两阶段检索（recall → rerank），只是把 rerank 从模型换成了 LLM，好处是能理解任务意图，坏处是成本和延迟。

**Q7：为什么强调"减少无关记忆干扰"？有实验数据吗？**
> 有定性观察。长期记忆最大的风险不是"记不住"，而是"记错/记多了导致模型行为漂移"。具体两个问题：
> 1. **上下文污染**：无关记忆占用 token，挤掉真正需要的上下文。
> 2. **行为干扰**：模型会过度遵从记忆里的约束，即使当前任务不适用。
>
> 所以我们的原则是**宁可少注入**：候选召回宽一点，严选严一点，注入量控制住。这个和 RAG 里"召回多、排序严"的思路一致。

**Q8：用户想删除某条记忆怎么办？**
> 提供记忆管理界面：按类别列出、单条删除、批量清空、开关（比如"不使用长期记忆"）。删除要同时清 ES 索引和 MySQL 记录，并保证一致（先删主存储标记，再异步清索引，兜底用定时对账）。

### Bullet 4：产品可观测性与数据闭环

> **原文**：围绕启动、活跃、会话、消息、文件、专家/助手、技能及应用等核心域建立 12 类标准事件；Desktop 侧采用本地持久化队列，每 30 秒批量刷新、单批处理 100 条、最多保留 2,000 条并支持离线重试，Server 侧基于业务事实异步派生事件并通过 `dedupHash` 实现幂等去重；埋点与分析异常不阻塞核心业务链路，同时避免采集消息正文和文件内容等敏感数据。

**一句话复述**：客户端把关键行为打成事件，本地攒批上报，服务端去重后入分析库，用来看产品数据；全程不能影响业务，也不能采集隐私内容。

**必答题链**

**Q1：12 类事件是怎么划分的？**
> 按**核心域**划分：启动、活跃（日活/留存相关）、会话（创建/切换）、消息（发送/接收/失败）、文件（上传/解析/引用）、专家/助手（选择/调用）、技能（调用/成功/失败）、应用（打开/使用）等。**每个事件带域、动作、时间戳、匿名用户 ID、设备/版本、上下文参数。**
> 划分原则是**跟着产品要回答的问题走**——不是"能埋的都埋"，而是"每个要监控的指标背后至少有一个事件"。

**Q2：为什么要客户端批量上报（30 秒 / 100 条 / 2000 条）？**
> 三个约束的平衡：
> - **30 秒**：延迟可接受（分析不需要实时到秒级），又不至于攒太久丢数据。
> - **100 条/批**：单次请求体的合理大小，避免单请求过大影响传输稳定性和服务端处理。
> - **2000 条上限**：本地队列的容量上限，防止离线过久导致本地存储无限增长。
>
> 触发条件是"**或**"：到 30 秒 或 攒够 100 条 就上报。这是典型的**批量 + 定时**双触发策略。

**Q3：本地持久化队列为什么必须"持久化"？**
> 因为要支持**离线重试**和**应用重启不丢**。如果放在内存队列里，用户离线或者应用被杀，数据就没了。持久化到本地（SQLite / 文件）后，重启时能继续上报。
> 上限 2000 条时采用**丢弃最旧**策略（FIFO 淘汰），因为新数据比旧数据价值高。

**Q4：`dedupHash` 怎么算？为什么需要幂等？**
> 幂等的必要性：网络超时会导致**客户端重发**（它不知道服务端到底收没收到），服务端也可能**重复消费**同一条消息（队列至少一次投递语义）。没有幂等就会重复计数，指标虚高。
> `dedupHash` = 对能唯一标识这条事件的字段做哈希，通常是 `事件名 + 匿名用户ID + 客户端事件ID(或时间戳) + 关键业务ID`。
> **注意**：不能用"事件名 + 用户 + 时间戳"就完事——同一秒内可能有多条同类事件。所以事件在客户端生成时就应该带一个**唯一的 eventId（UUID）**，服务端以它为主键做唯一约束或 Redis SETNX。
>
> 服务端"基于业务事实异步派生事件"的意思是：有些事件不是客户端打的，而是服务端根据业务动作（比如订单创建、文件解析完成）自己产生的，这类事件也要走同一套去重逻辑。

**Q5：「埋点异常不阻塞核心业务链路」怎么保证？**
> 四条纪律：
> 1. **异步化**：上报走独立线程/进程/队列，不在业务主路径上同步等待。
> 2. **超时 + 熔断**：上报接口设短超时，连续失败就降级为只写本地队列。
> 3. **异常吞掉但记录**：埋点代码的所有异常都捕获并写入本地错误日志，绝不向上抛。
> 4. **独立资源**：埋点用的网络连接、磁盘写入和业务隔离，避免互相影响（比如磁盘打满不能影响业务读写）。
>
> 一句话：**埋点是旁路（side-channel），不是主链路的一部分。**

**Q6：「不采集消息正文和文件内容」为什么重要？怎么保证？**
> 这是合规和信任问题：对话正文和文件内容属于用户敏感数据，可能含商业机密甚至个人信息。一旦埋点里带了这些，就等于把敏感数据复制到了分析系统，扩大了数据暴露面，也可能违反数据保护要求。
> 保证手段：**在埋点的 schema 层只允许白名单字段**（事件名、枚举值、ID、长度、耗时这类），正文类字段在客户端就截断/丢弃，服务端再做一次校验拒绝。**用 schema 约束而不是靠人自觉**，这是关键。

**Q7：这一条和 DFT 的关系？**
> 直接对应：DFT 的**测试数据闭环**。ATE 测试结果、覆盖率报告、fail log 都是"测试事件"，需要采集 → 去重 → 聚合 → 出看板 → 驱动改进。我在做的"批量上报 + 幂等去重 + 不阻塞主链路 + 敏感数据治理"这套，换个数据源就是测试数据平台。

## 3. 项目：教辅录题与审核平台｜2026.02–至今

### Bullet 1：整体

> **原文**：面向教辅录题场景独立设计并实现教材解析、自动切题、AI 质检、人工校对和入库流程；平台累计承载 6,862 本教材、72.9 万页 PDF、125.2 万道题目。技术栈：Vue 3 / Fastify / PostgreSQL / Redis / BullMQ / MinerU / 火山方舟。

**必答题**

**Q1：这个平台解决什么业务问题？**
> 教辅出版行业要把纸质/PDF 教材数字化成结构化题库。原来的做法是人工用 Excel、靠多个工具拼，效率低、易错、不可追溯。平台把"上传 PDF → 解析 → 自动切题 → AI 质检 → 人工校对 → 入库"整条链路做成一站式。

**Q2：数据量这么大，你的规模感可信吗？（会核实）**
> 6,862 本、72.9 万页、125.2 万题，平均一本 ~106 页、~182 题。这个数字在教辅场景是合理的（一本练习册几百道题很常见）。**如果面试官问"平均每页多少题"，你要能立刻算出来：125.2万 / 72.9万 ≈ 1.7 题/页。** 提前算好这些派生数字，被追问时秒答，可信度完全不一样。

**Q3：为什么用 Fastify 不用 Express/NestJS？**
> Fastify 的性能更好（schema 编译、更快的路由），原生支持 JSON Schema 校验和序列化，TypeScript 支持好。相比 NestJS，它更轻，项目一开始是单人开发，不需要 NestJS 那种完整的依赖注入和模块体系。

**Q4：为什么 PostgreSQL 不用 MySQL？**
> 需要 JSONB（存 MinerU 的块级结构和坐标）、需要更好的复杂查询能力、以及后续可以用 pgvector。另外题目和教材是多对多关系，PG 的索引和查询规划在这个场景更舒服。

### Bullet 2：可追溯的结构化切题

> **原文**：利用 MinerU 的块级坐标和目录结构，由大模型输出题号、题干、选项、答案、解析对应的源块 ID，再由服务端回填原文与坐标，避免模型直接改写正文，使字段可追溯至 PDF 原始区域；结合章节归属约束处理跨页、双栏与章节边界，通过"章节标题 + 题号"完成题答配对，解决题目页和答案页分离的问题。

**一句话复述**：不是让大模型抄一遍题目（会抄错），而是让它只输出"哪几个块是题干、哪几个块是选项"，正文由服务端从解析结果里原样取回。

**这是全篇最值得讲的一条，一定要讲透。**

**Q1：为什么要"让模型输出块 ID 而不是正文"？**

**核心答法**：

> 这是整条链路设计上最关键的一个决定，解决的是**大模型的不可靠性**问题。
>
> 如果让模型直接输出题干正文，会有三个无法接受的后果：
> 1. **改写风险**：模型会"顺手"修正它认为错误的表述、统一格式、补全缺失内容。教辅题目里的符号、下标、公式、空格都是业务信息，改了就错。
> 2. **不可追溯**：出了错只能人工重看整页 PDF，无法定位"这个字段来自 PDF 的哪一块"。质检和人工校对没法做。
> 3. **不可验证**：无法自动判断模型有没有编造内容。
>
> 改成输出块 ID 之后：
> - 正文由服务端从 MinerU 的结构化输出里**原样回填**，物理上不可能被改写。
> - 每个字段都带上了坐标（bbox），可以**渲染回原图做可视化核对**，也可以做自动校验（比如选项块是否在同一栏、是否垂直排列）。
> - 模型的任务从"生成"降级为"**分类和指认**"，这是 LLM 更擅长、更不容易出错的任务类型——判断"这一段是不是题干"比"抄写这一段"可靠得多。

**这句话是本条的灵魂："把生成任务降级为指认任务"。必须说出来。**

**Q2：MinerU 是什么？它输出什么？**
> MinerU 是一个开源的高精度 PDF 解析工具（上海 AI Lab），针对学术/文档场景。它输出的核心是**块级结构**：每个块有类型（标题/正文/表格/图片/公式）、内容、页码、以及**bounding box 坐标**。同时输出目录树（章节层级）。
> 我们用它的块级坐标做两件事：一是给大模型提供"块 ID → 内容"的映射，二是回填坐标用于后续的裁剪和可视化。

**Q3：为什么用 MinerU 不用其他（PyMuPDF / pdfplumber / 自己写）？**
> 普通 PDF 库只能给出文字和基础坐标，处理不了双栏、公式、表格、图片混排的复杂版面，而教辅 PDF 恰恰是这种。MinerU 用视觉模型做版面分析，输出的是**语义块**，这是必需的。自己训版面模型不现实。

**Q4：「跨页、双栏、章节边界」具体怎么处理？**

这是追问最密的地方，**必须能举具体例子**：

> 三种典型情况：
> 1. **跨页**：一道题从第 5 页底部延续到第 6 页顶部。处理方式是**先按题号/题干起始标记切出题目边界，再做页间拼接**——判断依据是前一页最后一块在页面底部、后一页第一块在页面顶部，且中间没有新的题号出现。
> 2. **双栏**：题干在左栏、选项在右栏，或者一道题横跨两栏。MinerU 会给出每块的坐标，我们**按 x 坐标聚类判断栏归属**，同一栏内按 y 排序，栏间按 左→右 或 上→下（跨栏题）处理。判据是栏的 x 范围有重叠且 y 范围连续。
> 3. **章节边界**：利用 MinerU 的目录树，把块归属到章节。当检测到新的章节标题时，强制切分当前题目——防止上一章的最后一题和下一章的第一题粘连。

**Q5：「章节标题 + 题号」配对是怎么做的？为什么需要它？**

> 问题的来源：教辅书里**题目和答案是分开排的**——前面是题目区，后面（或书末）是答案解析区。所以不能"题目后面跟着的就是它的答案"。
>
> 配对键选 `(章节标题, 题号)` 这个二元组，原因：
> - **只用题号会冲突**：不同章节都有"第 1 题"。
> - **只用章节标题不够精确**：一个章节有很多题。
> - 二元组在单本书内具有**唯一性**，可以做哈希键做 O(1) 匹配。
>
> 实现上是两趟：第一趟扫描所有块，收集所有"题目起点"和"答案起点"，分别建立 `(章节, 题号) → 块区间` 的字典；第二趟做字典键的交集匹配，未匹配上的单独报出来让人工处理（可能有缺题号、题号错印的情况）。

**Q6：如果书里题号不规范（漏印、错印、重复）怎么办？**
> 兜底三级：
> 1. **模糊匹配**：题号做归一化（中文数字→阿拉伯数字、"1." 和 "1、" 和 "(1)" 统一）。
> 2. **顺序推断**：如果相邻题号连续（比如 3、4、5），中间缺一个可以通过位置推断补上。
> 3. **人工兜底**：无法自动配对的标记出来，进人工校对队列。**这一层必须有，而且要能说出它在系统里的位置**——这是"系统设计完整性"的体现。

**Q7：怎么保证模型输出的块 ID 是合法的（不幻觉）？**
> 关键校验：
> 1. Prompt 里把候选块列表作为**受限选项集**给出，明确要求只从列表里选。
> 2. 输出后用 JSON Schema 校验格式。
> 3. **服务端做合法性校验**：块 ID 必须存在于本次解析结果中，否则丢弃该字段并记录。
> 4. **结构性校验**：选项块应该在题干块之后、坐标应该在版面合理位置、数量应该匹配（选择题 4 个选项）。
>
> 只有全部通过才落库，否则进人工队列。**"无效输出不进库"是原则。**

**Q8：这一条和 DFT 的可迁移点？**
> **可追溯性**是共通的。DFT 里 pattern 要能反查"这个 pattern 覆盖了哪些故障"，覆盖率下降要能定位"是哪个模块、哪次改动"。我做的是"每个字段都能溯源到 PDF 原始区域"，方法论上是同一套：**不信任中间产物，一切以原始数据为锚点，用 ID 和坐标建立可回溯链路。**

### Bullet 3：长任务调度与断点续跑

> **原文**：基于 BullMQ 承接 PDF 拆页、MinerU 解析、OCR 和自动切题，接口返回 `jobId`，Worker 异步消费，前端通过 SSE 获取进度；以批次 checkpoint 实现失败断点续跑，自动跳过已成功批次；通过输入内容哈希 + Prompt 版本去重及 Redis 锁防止重复发起，避免重复执行与计费，并接入 Prometheus + Grafana 监控任务 P95、队列积压与 Worker 心跳。

**Q1：为什么必须异步？为什么用 BullMQ？**
> 一本教材的完整链路（拆页 → 解析 → OCR → 切题）可能要几分钟到几十分钟，HTTP 请求不能挂着。异步化的标准做法：接口只做参数校验 + 入队 + 返回 `jobId`，处理交给 Worker。
> 用 BullMQ 因为：基于 Redis，部署简单；原生支持重试、退避、优先级、并发度控制、延迟任务、任务事件；和 Node 生态（Fastify）天然契合。备选是 Celery（Python）或 RabbitMQ，但我们后端是 Node，BullMQ 的集成成本最低。

**Q2：任务怎么拆分？粒度怎么定？**
> 分两级：**教材级任务（父）** 和 **批次级任务（子）**。
> - PDF 拆页后按批次（比如每 20 页一批）拆成子任务，这样单个子任务失败只影响一批，重试成本低。
> - **粒度权衡**：批次太小 → 任务数爆炸，调度开销和 Redis 压力大；批次太大 → 单次重试代价高、并行度低。20 页左右是我们在"重试成本"和"调度开销"之间的折中。

**Q3：checkpoint 断点续跑具体怎么做？**

**这是本条的核心，必须讲清数据结构**：

> 每个批次任务完成后，在**教材级的任务状态记录**里标记该批次为 `done`（存批次 ID 列表或者用位图/JSON）。
> 任务整体失败重试时，Worker **先从状态记录里读出已完成批次列表，跳过它们**，只处理未完成的批次。
> 关键设计点：
> 1. **checkpoint 必须持久化**（Redis 或 PostgreSQL），不能只在内存里——Worker 重启就没了。
> 2. **幂等**：已完成批次的产物（解析结果、切题结果）要按批次 ID 唯一键写入，重复执行不会产生重复数据。
> 3. **部分成功的处理**：有些批次失败几次后仍然失败，不能无限重试阻塞整体。策略是设最大重试次数，超过后标记为 `failed` 并让整体任务进入"部分完成"状态，把失败批次报给用户手工处理。
>
> 价值：一本 300 页的书如果跑到第 280 页挂了，不用从头再来，省掉绝大部分重复的 LLM 调用和计费。

**Q4：为什么要用「输入内容哈希 + Prompt 版本」做去重？**

> 因为**重复执行 = 重复花钱**。LLM 调用是按 token 计费的，MinerU 解析也是算力成本。重复发起的来源：用户手抖点两次、网络重试、前端状态不同步。
>
> 去重键 = `hash(文件内容) + prompt_version + 处理参数`。
> - **文件内容哈希**：同一个文件重复上传不重复处理。
> - **Prompt 版本**：这一条很关键——如果只按文件哈希去重，那**改了 Prompt 想重跑就永远跑不出来**。带上版本号后，换版本就是新任务，符合预期。
> - **处理参数**：比如 OCR 开关、切题策略变了也应该重跑。
>
> 这个设计体现的是"去重不是简单地按文件，而是要区分**什么变了才该重跑**"。

**Q5：Redis 锁怎么用？锁的坑在哪？**

> 用 `SET key value NX PX 30000` 实现分布式锁，防止同一个文件被并发处理。
> 坑必须知道：
> 1. **锁要设过期时间**，否则 Worker 崩了锁永远不释放（死锁）。
> 2. **过期时间可能不够**：任务跑 10 分钟但锁只设 30 秒，锁提前释放导致并发。解决：**看门狗续期**（后台定时给锁续命）。
> 3. **删锁要校验持有者**：用 Lua 脚本做 `GET == myToken` 才 `DEL` 的原子操作，否则可能删掉别人的锁。
> 4. **Redlock 的争议**：多 Redis 实例的 Redlock 在理论上有争议（依赖时钟），我们单实例部署，用简单锁 + 数据库唯一约束兜底就够了。
>
> **兜底很重要**：最终一致性靠数据库的唯一约束（`process_key` 唯一索引），锁只是性能优化，不是正确性保证。**这句话说出来非常加分。**

**Q6：SSE 怎么做进度推送？和 WebSocket 怎么选？**

| | SSE | WebSocket |
|---|---|---|
| 方向 | 单向（服务端→客户端） | 双向 |
| 协议 | HTTP/1.1 长连接 | 独立协议，需 Upgrade |
| 自动重连 | 浏览器原生支持 | 需自己实现 |
| 二进制 | 不支持 | 支持 |
| 代理/防火墙友好度 | 好（就是 HTTP） | 一般 |
| 适用 | 进度推送、日志流、大模型流式输出 | 双向实时通信、协作编辑、游戏 |

> 我们只需要服务端单向推进度，SSE 足够且更简单。需要注意：SSE 在 HTTP/1.1 下浏览器对同域名连接数有限制（6 个），HTTP/2 下没有这个问题；另外要处理**断线重连后的进度补偿**（重连时先拉一次当前状态）。

**Q7：Prometheus + Grafana 监控了哪些指标？为什么是这几个？**
> - **任务 P95 时长**：平均值会被快任务拉低，看不出长尾。用户抱怨的永远是慢的那 5%。
> - **队列积压（waiting / active / delayed 数量）**：积压 = 处理能力跟不上，是最直接的容量信号。
> - **Worker 心跳**：Worker 挂了队列不会报错，只会静默积压。心跳是发现"机器死了"的唯一手段。
>
> 告警策略：Worker 心跳超时告警、P95 超阈值告警、队列积压超阈值告警。
> 这三个指标的组合覆盖了**"慢""堵""死"**三种故障模式，这是设计监控指标时的思考方式。

### Bullet 4：多模态质检与安全写回

> **原文**：使用文本模型输出包含问题位置、原文和修改建议的结构化问题单，再按 MinerU 坐标裁剪 PDF 原图供视觉模型复核，过滤缺乏原图依据的误报；写回前校验原文唯一定位、内容哈希与稿件版本，仅自动修复通过校验的问题，其余交由人工处理。已覆盖 80 本教材、14.4 万道题，内容准确率由约 95% 提升至 98%，单本教材平均抽检耗时由 40 min 降至 18 min。

**Q1：为什么用两个模型（文本 + 视觉）复核？**
> 因为纯文本质检有一个系统性缺陷：**文本模型看不到版面**。题目里的上下标、分数线的位置、括号的范围、图表的归属，在纯文本里会丢失语义。模型会基于残缺信息报出误报。
> 加视觉复核后，用 MinerU 的坐标把**原文区域裁剪成图**给视觉模型看，让它判断"这个问题是否真的有原图依据"。
> 效果是**过滤掉大量缺乏原图依据的误报**——这是这段设计的核心价值：**不是提高召回，是提高精确率**，减少人工复核的负担。

**Q2：视觉复核怎么知道该裁哪一块？**
> 问题单里带了**原文和位置信息**，位置信息就是块 ID/坐标。用坐标加一点 padding（避免切断文字边缘）从 PDF 渲染图里裁剪出区域，再喂给视觉模型。

**Q3：「缺乏原图依据的误报」具体长什么样？**
> 举几个真实类型（能举例就显得真做过）：
> - 模型说"选项 B 缺少单位"，其实单位在题干的图里。
> - 模型说"答案解析和题目不匹配"，其实是它把双栏的左右两块读成了上下顺序。
> - 模型说"公式错误"，其实是纯文本里公式符号被线性化导致的误解。
>
> 这三类的共同点是：**文本层面看起来确实有问题，但看原图就知道没问题**。

**Q4：「写回前校验原文唯一定位、内容哈希、稿件版本」三个校验分别防什么？**

| 校验 | 防的问题 |
|---|---|
| **原文唯一定位** | 修改建议说"把'下列说法正确的是'改成'以下说法正确的是'"，但书里这句话出现 20 次——必须能唯一定位到**具体某一道题的某一个字段**，否则改错地方。做法是把定位限定在题目 ID + 字段 + 块 ID 的范围内 |
| **内容哈希** | 从质检到写回之间，内容可能被人工改过（或另一个流程改过）。哈希不一致说明**待改的原文已经变了**，此时应用旧的修改建议会破坏内容 |
| **稿件版本** | 防止**并发写**。两个质检任务基于同一版本的稿件生成建议，如果都写回，后写的会覆盖前者。用乐观锁（版本号 CAS）解决 |

> 这三个校验合起来是典型的**乐观并发控制 + 内容一致性检查**。核心思想：**自动修改是不可逆的高风险操作，必须在写入前把所有可能的不一致都挡住，宁可退回人工。**

**Q5：为什么不全部自动修复，只修"通过校验的"？**
> 精度优先。准确率从 95% 到 98% 是靠"只改有把握的"实现的——如果全改，误改会把准确率拉低。人工处理剩下的是**成本可控的**，因为数量少了。
> 这个取舍是：**自动化的目标是减少人工工作量，不是消灭人工。** 一个会改错的自动化系统比没有自动化更糟。

**Q6：95% → 98% 和 40min → 18min 怎么测出来的？**（**这是最容易被追问穿的地方**）

**必须诚实且有方法**：

> - **准确率**：用**人工抽检**作为基准。固定抽检规则（比如每本教材随机抽 N 道题，人工核对字段是否正确），统计抽检样本里的正确率。85 本教材、14.4 万题里我们抽检的是 80 本范围内的样本。
> - **抽检耗时**：统计单本教材从进入质检到人工确认完成的总耗时，取平均。
>
> **局限我要说明白**：
> 1. 抽检是**抽样**不是全量，所以这个数字是估计值，有置信区间。
> 2. 抽检的样本不是严格随机（早期版本可能抽得更多），所以前后对比可能有偏差。
> 3. 准确率的口径是"字段级正确率"还是"题目级正确率"会有差异。
>
> 如果面试官追问，我会说"这个数字来自人工抽检统计，我可以说清口径和抽样方式，但它不是全量精确测量"。**主动承认统计局限性，比硬撑一个数字安全得多。**

## 4. 竞赛与获奖

### 4.1 ICCV 2025 Perception Test Challenge｜冠军

> **原文**：面向多项选择视频问答中的细粒度视觉辨别、遮挡推理与选项位置偏置问题，基于 Qwen2.5-VL-7B 完成视频问答指令微调，并设计困难题型挖掘、课程学习和选项乱序增强；推理阶段结合题型专用 Prompt、TTA 及多模型按题型集成，最终获得测试集 80.9% 准确率。

**必答题**

**Q1：这个比赛考什么？**
> Perception Test 是 DeepMind 提出的视频/多模态感知评测基准，考察模型对视频的细粒度感知和推理能力（记忆、抽象、物理、语义等）。2025 年的挑战赛是多项选择视频问答（MC-VQA）。

**Q2：「选项位置偏置」是什么？为什么重要？**
> 模型倾向于选某个固定位置的选项（比如总选 A，或总选最长的那一项），而不是真正理解内容。这是 MC-VQA 的经典陷阱：测试集上的高分可能来自偏置而非能力。所以要**统计各选项位置的选择分布**，用**选项乱序增强**（训练时随机打乱选项顺序并同步调整 label）来打破这个捷径。

**Q3：「困难题型挖掘」怎么做？**
> 先跑基线，按题型统计准确率，找出准确率最低的题型（比如遮挡推理、时序关系）；然后针对这些题型**定向采样或合成更多训练样本**，或者对这部分样本加权。本质是**课程学习 + 难例挖掘**。

**Q4：「课程学习（Curriculum Learning）」是什么？**
> 按难度从易到难安排训练数据。先用简单样本让模型收敛到基本能力，再逐步引入困难样本，避免一开始就被难例带偏。实现上可以用分阶段训练，或对样本动态加权。

**Q5：「TTA」是什么？**
> Test-Time Augmentation，测试时增强：对同一个测试样本做多种变换（视频抽帧位置、裁剪、翻转等），分别推理后**投票或平均**，提升鲁棒性。代价是推理成本成倍增加。

**Q6：「多模型按题型集成」怎么做的？**
> 不同模型在不同题型上表现不同。做法是：先在验证集上按题型统计各模型的准确率，为每个题型选择在该题型上表现最好的模型（或加权组合），推理时先判断题型再路由到对应模型。这比无差别平均更好，因为**平均会被弱模型拖累**。

**Q7：80.9% 是什么水平？**
> 这是挑战赛测试集上的准确率，获得了该赛道冠军。**注意不要过度解读**——这是特定赛道、特定数据集上的结果，不能等同于通用视频理解能力。

**Q8：这个和 DFT 有什么关系？**
> 说实话关系不大，这是 AI 算法能力。如果面试官问"这跟 DFT 有什么关系"，诚实回答：
> **"竞赛本身和 DFT 不直接相关，它证明的是我的算法实现能力、实验设计能力和在压力下拿结果的能力。我不会把它当成 DFT 相关的经历来讲。"**
> **诚实 > 硬扯。** 硬扯关系反而失分。

### 4.2 "天翼云息壤杯" AI 大赛：数学推理｜三等奖

**必答题**

**Q1：蒸馏怎么做？**
> 用 Qwen2.5-Math-72B 作为教师模型，对数学题生成 CoT（Chain-of-Thought）推理过程，得到 10 万条样本；然后用这些样本对 Qwen3-8B 做 LoRA 微调。这是**知识蒸馏 + SFT** 的组合：教师提供推理过程（不只是答案），学生学推理模式。

**Q2：为什么要用 Math-Verify 和 Qwen2.5-72B 两道校验？**
> 因为**教师模型也会错**，直接用它的输出训练会把错误教给学生（噪声放大）。
> 两道校验：
> - **Math-Verify**：基于规则/符号计算的答案验证器，对能符号化求解的题做精确判断，**确定性高但覆盖有限**。
> - **Qwen2.5-72B 复核**：对 Math-Verify 覆盖不到或答案有争议的题，用另一个大模型判断推理过程是否合理，**覆盖广但可能出错**。
>
> 两者组合是"规则 + 模型"的互补：规则保证高置信样本的准确性，模型扩展覆盖范围。

**Q3：LoRA 是什么？为什么用它？**

必背：

> LoRA（Low-Rank Adaptation）是在**冻结预训练权重**的前提下，给权重矩阵注入一对低秩矩阵 `B×A`，训练时只更新这两个小矩阵。
> 前向计算变成 `W' = W + BA`，其中 `A ∈ R^(r×d)`、`B ∈ R^(d×r)`，秩 `r` 远小于原维度 `d`。
> 优点：
> 1. **参数量极小**（通常只占原模型的 0.1%–1%），训练显存需求大幅下降。
> 2. **不破坏原模型能力**，且可以为不同任务训练不同 adapter，**推理时动态切换**。
> 3. **不改变推理延迟**：训练完后可以把 `BA` 合并回 `W`，推理和原模型完全一样。
>
> 缺点：低秩假设不总成立，容量有限；对差异极大的任务可能不如全参微调。

**Q4：8 卡昇腾 910B 上做 LoRA，遇到什么问题？**
> 昇腾用的是 CANN 软件栈而不是 CUDA，所以生态兼容性是主要难点：PyTorch 算子要跑在 torch_npu 上、部分算子不支持需要改写、分布式训练要用 HCCL。**这类"生态迁移"的排障经历本身就是加分项**，能具体讲一两个踩坑比泛泛而谈好。

**Q5：38% → 62% 提升的原因是什么？**
> 三个来源：
> 1. **领域数据**：教辅/竞赛类数学题的模式和通用语料不同，SFT 让模型适应了这个分布。
> 2. **CoT 训练**：学会了"分步推理"的输出格式，减少跳步错误。
> 3. **数据质量**：双重校验过滤掉了错误标注，避免噪声训练。
>
> 也要说明局限：这是在特定测试集上的提升，且"正确率"的判定口径要清楚（最终答案匹配）。

### 4.3 WACV 2025 目标距离估计｜冠军 / CVPR 2025 少样本目标检测｜三等奖

简历里这两条只写了名字。**面试官一定会问细节，必须准备好**：

> **建议准备 3 句话**：任务定义、你的方法、结果。
> - **WACV 2025 目标距离估计**：任务是从单目/双目图像估计目标的物理距离。方法：（按你实际做的写，比如基于深度估计 + 相机标定 / 单目深度 + 目标框回归）。结果：冠军。

## 5. 专业技能条目逐条答辩

### 5.1 数字电路与 RTL / DFT 基础

见 `07-DFT面试准备-数字电路与RTL基础.md`、`08-DFT面试准备-SCAN与ATPG.md`、`09-DFT面试准备-MBIST与存储器测试.md`。这三章覆盖了简历上这两条里的**每一个名词**。

### 5.2 Agent / LLM

> **原文**：Agent Runtime、Agent Loop、Tool-use、MCP、ReAct、RAG、上下文工程、长短期记忆、Prompt 设计、LoRA 微调、vLLM 推理部署。

**高频八股（速答版）**：

- **MCP（Model Context Protocol）**：Anthropic 提出的标准化协议，让 LLM 应用用统一接口连接外部工具和数据源。核心是 **Server 暴露 Resources（数据）/ Tools（动作）/ Prompts（模板）**，Client（Agent 宿主）连接并注入。价值是**消除 M×N 集成问题**（M 个模型 × N 个工具，从 M×N 个适配器变成 M+N）。
- **ReAct**：Reasoning + Acting。让模型交替输出"思考"和"动作"，用动作结果更新下一轮思考。相比纯 CoT 的优势是能获取外部信息、能纠错。
- **RAG**：检索增强生成。检索（向量/关键词/混合）→ 重排 → 注入上下文 → 生成。关键难点：分块策略、召回率 vs 精确率、rerank、幻觉引用、上下文长度预算。
- **上下文工程**：不只是写 prompt，而是管理"进入上下文窗口的一切"——系统提示、工具定义、历史压缩、检索结果、记忆注入、输出预留。核心是**预算分配**。
- **vLLM**：高吞吐 LLM 推理引擎。核心技术是 **PagedAttention**（把 KV Cache 按页管理，像操作系统虚拟内存一样，大幅减少显存碎片，提升并发）和 **continuous batching**（请求级动态批处理，不等整批结束）。

### 5.3 后端

> **原文**：Python（FastAPI / Django）、Node.js（Fastify / NestJS）、RESTful API、异步编程、SSE / WebSocket、PostgreSQL / MySQL、Redis、Celery / BullMQ、JWT。

**可能的追问**：
- **FastAPI vs Django**：FastAPI 异步、轻量、Pydantic 校验、自动 OpenAPI；Django 全栈、ORM 强大、admin 开箱即用、生态成熟。选型看场景。
- **PostgreSQL vs MySQL**：PG 支持 JSONB、更丰富的索引（GIN/GiST）、窗口函数更强、事务和并发控制更严格（MVCC 实现不同）；MySQL 生态和运维更普及。
- **JWT 的坑**：无法主动失效（需配合黑名单/短 TTL + refresh token）、payload 明文可读（不能放敏感信息）、需要防重放（jti + 时间窗）。
- **Redis 持久化**：RDB（快照，恢复快，可能丢数据）、AOF（追加日志，丢得少，文件大）。生产一般混合。

### 5.4 前端

> **原文**：Vue 3、TypeScript、Vite、Vue Router、Pinia、Element Plus / Ant Design Vue、组件化开发、状态管理、动态路由、SSE / WebSocket 实时通信。

**高频**：Vue 3 的 Composition API vs Options API；响应式原理（Proxy vs defineProperty）；Pinia vs Vuex（去 mutation、TS 友好、模块化天然）。

### 5.5 Linux / 工程化

> **原文**：熟悉 Linux 常用命令、Vim、grep / sed / awk、进程与日志排查，使用 Python / Shell 编写自动化与批处理脚本；Git、Docker / Docker Compose、MinIO、Prometheus + Grafana、Nginx。
