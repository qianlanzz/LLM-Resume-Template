# 携程 AI 面 · 参考答案


## 题 1. 分享一次你主动找到核心问题，并提出解决方案的经历

我说一个不是别人安排、是我自己先发现的事。当时在二十八所做模型管理平台，平台能按名字和分类搜模型，但业务那边还是老找不着。他们搜的是"适合做小目标检测、最好能在边缘盒子上跑"这种话，但库里存的是模型名和版本号，关键词完全对不上，搜出来就是空，然后又跑来问我们。

大家一开始觉得是搜索体验不好，想加同义词、加标签。我拉了两周的失败查询和人工代查记录看了一下，发现问题不在前端，是用户说的话和库里的数据根本不在一个层面上——人家说的是任务和约束，库里存的是名称和版本。再怎么加标签，还是在错的层上补。

所以我提了个不一样的做法：把模型的名称、分类、描述、关联数据集、版本说明拼起来做成一段检索文档，然后用向量检索来匹配任务描述，再拿名称做一轮重排序。我先拿 30 条真实的搜索句子，对比旧搜索和新方案各自能找到几个，确认确实是"任务到资源"这个缺口在卡。

落地的时候也没搞太大动作，先把索引跟着模型增删改自动走，查询慢的做个缓存。上了之后，业务那边"描述任务但不知道模型叫啥"的代查明显少了。

后来我遇到类似的事情，第一反应不是加功能，是先搞清楚：用户卡住到底是界面不好用、数据不对，还是他的问法和数据根本就不在一个空间里。

## 题 2. 项目中最大的困难是什么？

我说教辅录题那个项目吧，因为这个困难最让我印象深。

表面上看很简单：上传 PDF，出来题干、选项、答案、解析。但真正做的时候全是坑——教材是双栏的，题在前面答案在书后面，一道题跨两页，公式被拆开，这都是常事。你要是直接把一页字交给模型让它"整理成题目"，它特别自觉地帮你润色句子、补解题步骤、把旁边栏的内容拼进来。但题库不能接受这种美化，因为录完了还要对着书验收，你改过措辞了，验收的时候就发现对不上，那等于假数据。

其实困难分两层。一层是技术上的，模型天然就爱生成、不擅长忍住不改。另一层是人，录题的老师担心自动化一上，错题哗哗进库，他们还得一个个去擦屁股，宁可慢也不愿意背这个锅。

所以我把模型的任务改了——不让它生成题目正文，只让它告诉我"题干是版面上哪些块、选项是哪些块、答案是哪些块"，真正的文字和坐标由程序去回填。跨页、双栏这些，靠目录路径和页面归属来约束；如果某道题实在拿不准归哪章，那就漏掉，标给人工补。漏了可以补，切错了一整章都会被污染。

跟业务沟通的时候我也没承诺"全自动"。我说的是：自动出来的每一项都能点回原书，拿不准的一定进人工，系统不会偷偷改措辞。他们接受了之后，自动化才真正进了生产。

后来这套跑了两千多本、快三十万页，平台整体接到了六千多本。我自己回头看，最难的往往不是模型够不够强，是你能不能让它在业务能接受的范围里，只做它该做的事。

## 题 3. 你怎么定位问题根因？

说实话我定位问题基本不会先想"换个模型试试"或者"提示词再写长一点"，我会先问自己：这个现象，最简单的解释是什么，我怎么验证它。

有一次教辅质检上线后，抽检老师反馈说"AI 改错题了"。可能的原因有好几个：模型不行、提示词没写好、老师用法不对。我先抽了二十来道被改错的题，列了张表，看四个东西：模型当时看到的文本、它给的理由、PDF 原图上到底印了啥、系统有没有把改动写回去。

一对就发现了——很多"错误"在文字上看确实别扭，答案短、解析跳步、选项顺序怪，但原书上就是这么印的。文本模型看不到版面，它只是凭做题经验觉得"这题不太对"。所以根因不是它不会质检，是它根本没看到原图，缺判决需要的证据。提示词写再长也解决不了"没看见"这件事。

改法就清楚了：让文本模型先出一份怀疑清单，然后把 PDF 对应区域裁出来给视觉模型核对，没有原图支持的就扔掉。最后写回的时候还得查原文位置对不对、版本对不对。搞完之后误改挡住了，抽检也从一本大概 40 分钟降到 18 分钟左右。

我现在排查问题就几步：先复现，没复现不下结论；然后一层层看，输入、中间结果、输出、写回，到底哪一步丢的；再做最小的对照实验，只改一个变量看现象变没变；最后写成一条以后能防住的规则。时间紧的话先止血，但止血和定位得分开说——临时绕过去不代表找到原因了。

## 题 4. 有没有一次失败经历？怎么复盘的？

有，而且是我自己决策错了，不是别人的问题。

教辅切题能跑之后，抽检还是很慢，我就想赶紧把"找错"也自动化。第一版只上了文本模型去扫题干和答案，输出修改建议，而且我当时还想让建议直接自动写回去，觉得这样才算真正的闭环。

结果给老师一用就暴露了。它确实能找到一些格式问题和明显错配，但同时也会把书上印对的内容改掉。老师说得很直接：漏一道错题我们忍了，但系统偷偷改对的题，那整个题库就不能信了。这不是什么小体验问题，是失败。我把"模型能提出怀疑"当成了"模型有权改数据"，这个等号不成立。

复盘的时候我没推给"模型有幻觉、很正常"，是我自己把写权限放太早了。正确的顺序应该是：先证明它能稳定发现问题，再证明修改有原图依据，最后才开自动写回，而且还得有版本锁。我当时急着展示一个完整的自动化，三步合成了一步。

后面怎么改的呢：自动写回先关了，所有建议只进问题单。补了视觉复核，没有原图支持的直接扔。写回恢复以后得过三道关——原文能唯一定位、哈希对得上、没人正在编辑，过不了就给人。后来质检覆盖了 80 本、14 万多题，准确率大概从 95% 到 98%。但这些数字是后面的事，前面那版如果继续自动写，数字再好看也没意义。

这次之后我给自己定了条规矩：会改生产数据的能力，默认关着，拿证据来开。

## 题 5. 团队成员意见不一致时怎么办？

说一次比较硬的分歧。在二十八所做检索的时候，我觉得应该补语义检索，因为用户就是在用任务描述来搜。但有个同事觉得库才几千条，把名称和标签补齐，关键词搜索就够了，上向量检索是把系统搞复杂。

说实话他的担心有道理。复杂度和稳定性确实是问题。但我觉得用户搜的方式和库里的字段根本对不上，补词堵不住这个缺口。

这种时候我肯定不能靠嗓门大，我当时也没那个位置。我做的事情是先把争论从"哪个方案更先进"拉回来，变成几个大家能一起看的具体问题：现在失败检索里有多少是补完标签就能好的？持续补标签要花多少人力？语义检索在这个规模上真的会很难维护吗？先把目标统一了——就是减少代查、同时别加一个不稳的东西——然后看数据。

我做了两件具体的事。一个是把两周的代查记录标成三类：缺别名、缺分类、任务描述对不上。让他看到：别名问题确实有，但有一类再怎么补词也解决不了。另一个是搞了个最小的检索服务，不接主系统，只拿那 30 条真实问法跑一下。

有了这些东西，讨论就不是谁对谁错了，变成怎么取舍。最后的落地方案是并存——关键词保留，语义检索先灰度给几个最常代查的人，索引更新出问题不影响原来的搜索。他的担心被写进了方案里，不是口头安抚。

我后来处理分歧就这个套路：先承认对方在保护什么，然后把争论变成能用数据看的问题，再做小范围验证。比争赢了管用。

## 题 6. 有没有推动别人接受你方案的经历？

有。教辅质检能出修改建议以后，有个想法是：既然已经有原文和改法了，直接写回题库，人工只做抽查，这样才像话。我当时反对立刻这么做，因为我已经见过模型在没看到原图的时候改错题了。但你要是只说"模型会幻觉"，听起来就像技术团队在保守。

所以我没反复强调风险，换了个做法——拉着大家一起验收。我挑了三类真实题目：书上印得就很怪的、OCR 明显串行的、答案和解析分两页的。每类都给大家看三个东西：模型的建议、原图长什么样、如果当时自动写回会变成啥。看完之后大家自己就感觉到了：有些自动写是赚的，有些是会出事的。不用我再多解释。

然后我提的方案不是"全面人工"，而是拆开权限。有原图依据、能定位、没人在编辑的，可以自动修；只有文本怀疑的，进问题单给人看；有人正在改的稿子，等锁。同时约好两周后复盘：有没有新的误改、抽检时间降了没有。有验收条件，方案就不是我一个人的口味。

后来覆盖了 80 本，抽检时间差不多从 40 分钟降到 18 分钟，也没再出现第一版那种批量改错。他们接受的是一个可进可退的方案，不是"听我的"。

## 题 7. 描述一个你需要快速学习新技术的经历

我之前在做 Agent 项目的时候，发现单纯把大模型和工具接起来并不难，真正困难的是 Agent 跑复杂任务时会出现工具调用失败、流程中断、死循环，以及出了问题以后很难定位。所以当时我需要比较快地补齐 Agent Harness 和评测这块的知识。

我的做法不是先大范围看资料，而是先把问题拆成几个最核心的能力：工具调用、状态管理、重试机制、Trace 记录和任务评测。然后我会优先看官方文档、一些成熟开源 Agent 项目的实现，再自己做最小 Demo 验证，比如记录每一步模型输入输出、工具调用结果和耗时，再基于这些 Trace 分析 Bad Case。

后面我把这套思路用到了实际 Agent 流程里，不再只是看最终答案对不对，而是能定位到底是模型规划错了、工具选错了，还是上下文和 Harness 设计有问题。这样后续优化 Prompt、工具描述或者执行流程都会更有依据。

这段经历让我形成了一个习惯：遇到陌生技术时，我会先从实际问题出发，快速找到最小知识闭环，然后通过 Demo 和评测验证，而不是一开始就把所有资料学完。

## 题 8. 同时有多个任务时怎么确定优先级？

如果同时有多个任务，我一般会先看三个维度：业务影响、截止时间和依赖关系。

我会先把影响核心目标、时间最紧，或者会阻塞其他人的任务优先处理。比如一个问题如果不解决，后面的开发和测试都没法继续，那它的优先级通常会比一个独立的小优化更高。

对于优先级接近的任务，我会再看投入产出比，优先做能够快速降低风险、尽早验证关键假设的事情。尤其是在 Agent 项目里，我会先解决影响任务完成率、稳定性这类核心问题，再去做一些体验或性能上的细节优化。

如果任务确实很多，我也会及时和负责人同步优先级，避免自己凭感觉同时铺开很多事情。我的原则是先保证关键链路不被阻塞，再逐步处理次要任务。

## 题 9. 有没有主动做职责之外事情的经历？

有一次在做 Agent 项目的时候，我原本主要负责模型调用和 Agent 流程，但在联调过程中我发现，团队缺少一套比较系统的评测和问题定位机制。很多时候只能看最终结果对不对，但一旦效果不好，很难快速判断是 Prompt、工具调用、上下文还是执行流程出了问题。

这个其实不是我当时最核心的职责，但我觉得如果不解决，后面的迭代效率会比较低。所以我主动整理了一批典型 Bad Case，并补了一套 Trace 和评测流程，把每一步模型输入输出、工具调用结果、耗时和最终结果记录下来，再从任务完成率、工具调用正确率这些维度做分析。

后面这套东西不仅帮助我自己定位问题，也让团队在改 Prompt、换模型或者调整工具的时候，可以比较直观地看出效果到底有没有提升。

这件事对我来说最大的收获是，职责之外的事情我不会为了“多做”而做，而是会优先判断它是不是当前团队真正的瓶颈，如果能明显提升整体效率，我会愿意主动补上这一块。

## 题 10. 遇到需求模糊，或者需求跟实际描述不一致，怎么办？

我在公司实习的时候，确实遇到过需求比较模糊的情况。因为产品更多关注业务目标，不一定了解具体技术实现里的限制，所以有时候需求描述看起来很简单，但真正落地时会发现存在一些技术上的困难，或者实现成本和预期不太一致。

当时我的做法不是自己猜需求，而是先把我理解到的目标、技术难点和几个可能存在歧义的地方整理出来，然后拉上组长一起去和产品沟通。因为组长对整体项目和业务会更熟，我负责把具体技术问题讲清楚，比如哪些地方实现成本比较高、有哪些替代方案、不同方案会带来什么影响。

沟通之后，我们会把需求重新确认成比较明确的实现范围和验收标准，再继续开发。这样可以避免开发到一半才发现方向不对，也能让产品更清楚技术侧的边界。

这件事让我比较深的体会是，遇到需求模糊时，不能直接按照自己的理解做，也不能只是说“这个做不了”，而是应该把问题和可选方案讲清楚，和产品、组长一起把目标对齐之后再推进。

## 题 11. 最近在学什么 AI 技术？

最近主要在搞两块。一块是 Agent Harness，就是 Agent 外面那层运行框架——工具调用、上下文管理、状态维护、重试、日志、执行约束这些。我感觉现在做 Agent，难点已经不是把模型和工具接起来，而是怎么让它在复杂任务里稳定跑，出了问题能定位、能复现、能迭代。我最近比较关注怎么把这些能力做得更通用。

另一块是 Agent 评测。传统模型评测更多看单轮准确率，但 Agent 得看任务完成率、工具调用对不对、步骤合不合理、有没有死循环，还有成本和延迟。我最近在试的做法是通过 Trace 记录完整执行链路，再结合自动评测和人工 Bad Case 分析，判断问题到底出在 Prompt、模型、工具还是流程设计上。这部分我觉得对 Agent 真正能上生产非常关键。

## 题 12. 平时怎么学习 Agent / LLM？

我学这块基本就是"先看原理，再看好的实现，最后用项目去验证"，比较偏边学边做。

一方面我会持续看一些经典论文、官方文档和开源项目，像 Function Calling、RAG、Memory、MCP、ReAct 这些。看的时候重点不是记概念，是搞清楚它解决什么问题、适合什么场景、边界在哪。

另一方面我会直接去看一些成熟 Agent 框架和开源项目的源码，关注它们怎么做工具调用、上下文管理、状态维护和错误重试。遇到感兴趣的能力我会自己跑一个最小 Demo，然后放到实际项目里测，看它在真实数据上到底什么表现。

整体来说我不太会只看资料不动手，基本是带着具体问题去学，用实验结果来验证理解对不对。

## 题 13. 为什么选择 Agent 开发？

主要是因为我觉得 Agent 比单纯做一个聊天模型更接近真实应用。现在大模型本身已经很强了，但真正落到业务里，还得解决工具调用、任务规划、上下文管理、Memory、异常重试和评测这些问题，而这些正好是 Agent 开发最有挑战也最有价值的部分。

我比较喜欢这种既要理解模型能力、又要做工程系统设计的方向。一个 Agent 最终不是看"回答得像不像"，而是看它能不能真正完成任务、调对工具、稳定运行，出问题了能不能通过 Trace 和评测去定位和优化。

我自己之前也做过多模态和 Agent 相关的项目，所以后面就想继续往这个方向深入，重点做真正能上线、能评测、能持续迭代的 Agent 系统，不想只停在 Demo 层面。

## 题 14. 为什么选择携程？

主要是因为我觉得旅游场景非常适合 Agent 真正落地。旅行本身就是一个复杂的多步骤任务——理解用户需求之后，还得做搜索、行程规划、酒店和机票推荐、信息查询，甚至后续订单相关的操作。这里面天然涉及工具调用、任务规划、Memory 和多轮交互，不只是做一个聊天机器人。

另外我比较看重的是，携程有完整的真实业务和用户场景。Agent 做出来之后可以通过真实的任务完成率、用户反馈、延迟和成本去持续评测和优化，这跟我现在比较关注的 Trace 分析和 Agent 评测很对得上。

我自己之前一直在做多模态和 Agent 相关的项目，所以下一步不想只做 Demo，想参与一个真正能上线、能服务大量用户、并且可以长期迭代的 Agent 系统。我觉得携程这个场景和我的方向比较匹配。

## 题 15. 挑一个项目讲清楚你负责了什么

我讲教辅吧，因为这个是我独立设计和实现的。

业务问题很直接：教辅录题靠人和表格，一本书页数多、结构乱，录完了还得对着原书验收。我做的是把解析、切题、质检、人工裁决和入库串成一条能持续跑的生产线。

我真正做了三件有决策的事。

第一是切题时模型干什么。我没让它生成或润色题目，让它告诉我题干、选项、答案、解析分别对应版面上哪些块，文字由程序回填。这样每道题都能点回原图。拿不准的就漏掉给人补。

第二是质检谁有权改数据。第一版失败了，后来改成三段——文本模型出怀疑、视觉模型对照原图复核、写回前查位置和版本，过不了给人看。老师不是被替掉了，是从翻整本书变成处理问题清单。

第三是这条链路失败了怎么办、重跑了怎么不多花钱。切题、识别、质检都可能跑好几分钟，所以全部异步化，失败按批次续跑，成功的跳过，每次调用都留下模型和原始返回。没有这部分，前面两个都只是演示。

结果的话，平台大概 6862 本教材、72.9 万页、125.2 万题。解析稳定跑了 2225 本。质检 80 本、14.4 万题，找出大概 1.5 万个问题，抽检时间从 40 分钟降到 18 分钟左右。
