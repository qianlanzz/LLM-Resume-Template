# 携程 AI 面 · 行为面参考答案（润色版）

## 题 1. 分享一次你主动找到核心问题，并提出解决方案的经历

在二十八所做模型管理平台时，我发现一个问题：平台虽然支持按名称和分类搜索模型，但业务人员还是经常找不到自己想要的模型。后来我看了两周的失败查询和人工代查记录，发现真正的问题不是搜索框不好用，而是“用户怎么描述需求”和“系统里怎么存模型信息”不在一个层面上。用户会说“适合小目标检测、最好能在边缘设备上跑”，但库里主要是模型名、分类和版本号，关键词很难直接匹配。

所以我提出把模型名称、分类、描述、关联数据集和版本说明组合成检索文档，用向量检索匹配用户的任务描述，再结合名称做重排序。我先拿 30 条真实查询做小规模验证，确认效果以后再接入系统，并把索引更新和模型的增删改联动起来。

上线之后，业务人员因为“知道需求但不知道模型名”来人工询问的情况明显减少。这个经历让我意识到，遇到问题时不能急着加功能，先判断真正卡住用户的是界面、数据，还是两边表达方式本身就不一致。

## 题 2. 项目中最大的困难是什么？

我印象最深的是教辅录题项目。表面上看只是把 PDF 里的题干、选项、答案和解析提取出来，但真实教材里会有双栏、跨页、答案和题目分离、公式拆开等各种情况。更麻烦的是，大模型很容易“顺手”润色、补全或者重写内容，但题库要求尽量忠实于原书，这种生成式修改反而会带来风险。

所以我后来把模型的职责收窄：不让它直接生成题目正文，只让它判断题干、选项、答案和解析分别对应哪些版面区域，真正的文字和坐标由程序回填。对于跨页、双栏这些情况，再结合页面归属和目录信息做约束；实在不确定的题宁愿交给人工补，也不让错误结果污染整批数据。

另外，业务侧一开始也担心自动化会把错误大量带进题库，所以我没有强调“全自动”，而是保证每一项结果都能回到原书核对，不确定的进入人工处理。后来这套方案逐步跑进了生产。

这件事让我体会比较深的是，项目里最难的不一定是模型能力不够，而是怎么把模型能力限制在业务能够接受、能够验证的范围内。

## 题 3. 你怎么定位问题根因？

我定位问题时一般不会先想到换模型或者继续加 Prompt，而是先复现，再看问题到底出现在哪一层。

有一次教辅质检上线后，老师反馈“AI 把正确的题改错了”。当时可能的原因很多，比如模型能力、Prompt、使用方式或者系统写回。我先抽了一批被反馈的样本，把模型看到的文本、模型给出的理由、PDF 原图和最终写回结果放在一起对比。

对比之后发现，很多题从纯文本看确实不太合理，但原书就是这样印的。也就是说，模型不是不会判断，而是它缺少原图这个关键证据。继续优化文本 Prompt 解决不了“看不到原图”的问题。

所以后来把流程改成两步：文本模型先筛出可疑项，再把对应 PDF 区域交给视觉模型复核，没有原图依据的建议不允许写回。改完以后误改明显减少，抽检时间也从一本大约 40 分钟降到了 18 分钟左右。

我现在排查问题基本也是这个思路：先复现，再沿着输入、中间结果、输出和写回逐层看，最后用最小对照实验确认真正原因，而不是凭经验猜。

## 题 4. 有没有一次失败经历？怎么复盘的？

有一次比较典型的失败是在教辅质检项目里。第一版质检出来以后，我希望把自动化做得更完整，所以让文本模型发现问题后直接给出修改建议，并考虑自动写回题库。

实际给老师使用之后很快暴露出问题：模型确实能发现一些格式错误和明显错配，但也会把原书本身就比较特殊的内容当成错误去修改。老师当时反馈得很明确：漏掉一些问题还能人工补，但如果系统主动把正确内容改错，会直接影响整个题库的可信度。

复盘以后我发现，问题不只是“模型有幻觉”，更关键的是我把“模型能提出怀疑”和“模型有权修改生产数据”当成了一回事，权限放得太早了。

后来我先关闭自动写回，把建议全部变成问题单；再增加视觉复核，要求修改必须有原图依据；恢复写回以后又增加原文定位、版本校验和编辑状态检查。后面质检覆盖了 80 本、14 万多道题，整体准确率从大约 95% 提升到 98%。

这次经历让我形成了一个原则：涉及生产数据修改时，先证明判断可靠，再逐步开放权限，而不是一开始就追求全自动闭环。

## 题 5. 团队成员意见不一致时怎么办？

在二十八所做模型检索时，我和同事对方案有过一次比较明确的分歧。我认为应该增加语义检索，因为用户经常直接用任务描述来搜；同事觉得模型库规模只有几千条，把名称、标签和别名补齐，关键词搜索就够了，没必要增加系统复杂度。

我觉得他的担心是合理的，所以没有直接争论哪个方案更先进，而是先把问题变成几个可以验证的指标：现有失败查询里有多少是补标签能解决的，有多少是“任务描述和模型字段不一致”导致的；语义检索在当前规模下会增加多少维护成本。

我把两周的代查记录做了分类，又做了一个最小检索 Demo，用 30 条真实查询做对比。结果能比较清楚地看到，有一部分问题确实不是补标签能解决的。

最后我们没有把原方案推翻，而是保留关键词检索，同时把语义检索先灰度给部分用户，索引异常也不会影响原有搜索。

我觉得处理分歧最重要的是先理解对方在担心什么，再把争论转成可以用数据和实验验证的问题，而不是单纯争谁的方案更好。

## 题 6. 有没有推动别人接受你方案的经历？

在教辅质检项目里，模型已经能够给出修改建议以后，团队里有人希望直接自动写回题库，这样效率最高。我当时不太赞成立刻放开，因为前面已经出现过模型在缺少原图信息时误判的情况。

但如果只是说“模型可能会幻觉”，说服力其实不强。所以我挑了几类真实样本，包括原书本身表达特殊的、OCR 串行的、答案和解析跨页的，让大家一起看模型建议、PDF 原图以及如果直接写回会产生什么结果。

这样大家很快就能看到：有些修改可以自动做，但有些情况风险很高。基于这些样本，我提出按风险拆权限：有原图依据、能够唯一定位、版本也一致的可以自动修；只有文本怀疑的进入问题单；有人正在编辑的内容不自动写回。

最后这个方案被接受，后续既降低了抽检时间，也避免了第一版那种批量误改。

这件事让我感觉，推动方案落地时，单纯讲观点往往不够，最好能用真实数据、样本和可验证的结果让大家一起做判断。

## 题 7. 描述一个你需要快速学习新技术的经历

我之前在做 Agent 项目时，发现把大模型和工具接起来其实不难，真正麻烦的是复杂任务跑起来以后会出现工具调用失败、流程中断、死循环，而且出了问题以后很难定位。

当时我就需要比较快地补 Agent Harness 和评测这块的知识。我没有先大范围看资料，而是先围绕实际问题拆成几个最关键的能力：工具调用、状态管理、重试、Trace 记录和任务评测。然后优先看官方文档和成熟开源项目的实现，再自己做最小 Demo，把每一步模型输入输出、工具调用结果和耗时都记录下来。

后面把这套方法接进项目之后，遇到 Bad Case 就不再只是看最终答案对不对，而是能继续往下定位，到底是模型规划错了、工具选错了，还是上下文或执行流程出了问题。

这次经历让我形成了一个比较固定的学习方式：遇到陌生技术时，先围绕问题搭一个最小知识闭环，再通过 Demo 和真实数据验证，而不是一开始就把所有资料学完。

## 题 8. 同时有多个任务时怎么确定优先级？

如果同时有多个任务，我一般先看三个维度：业务影响、截止时间和依赖关系。

优先级最高的通常是会影响核心目标，或者会阻塞其他开发和测试的任务。对于优先级接近的事情，我会再看投入产出比，优先解决能够快速降低风险、验证关键假设的问题。

比如在 Agent 项目里，如果一边是任务完成率不稳定，一边是界面或性能上的小优化，我会先处理影响主链路稳定性的事情，因为它直接决定系统能不能正常用。

如果任务比较多、优先级不容易判断，我也会及时和负责人同步，而不是自己把所有事情同时铺开。我的原则是先保证关键链路和团队依赖不被阻塞，再处理次要优化。

## 题 9. 有没有主动做职责之外事情的经历？

有一次在做 Agent 项目时，我原本主要负责模型调用和 Agent 流程，但联调过程中我发现，团队缺少比较系统的评测和问题定位方式。很多时候只能看最终结果对不对，一旦效果不好，很难快速判断问题到底出在哪。

这部分并不是我最开始的核心职责，但它已经明显影响到后面的迭代效率，所以我主动整理了一批典型 Bad Case，并补了一套 Trace 和评测流程，把每一步模型输入输出、工具调用结果、耗时和最终结果记录下来，再从任务完成率、工具调用正确率等维度做分析。

这样之后，无论是改 Prompt、换模型还是调整工具，都可以比较清楚地看出改动有没有真正提升效果，也更容易定位退化原因。

我觉得职责之外的事情不是越多越好，关键还是看它是不是当前团队真正的瓶颈。如果一件事能明显提升整体效率，我会愿意主动把它补上。

## 题 10. 遇到需求模糊，或者需求跟实际描述不一致，怎么办？

我在公司实习的时候遇到过这种情况。产品通常更关注业务目标，不一定了解具体实现里的技术限制，所以有些需求从产品角度看比较简单，但真正开发时会发现实现成本、技术难点或者边界条件和预期不一致。

我当时不会自己猜着做，而是先把我理解的需求、技术难点和几个有歧义的地方整理出来，然后拉上组长一起和产品沟通。组长对整体业务和项目背景更熟，我负责把具体技术问题讲清楚，比如哪些部分实现成本比较高、有哪些替代方案、不同方案分别会有什么影响。

沟通之后，我们再把需求范围和验收标准确认清楚，然后继续开发。这样既能避免做到一半才发现方向不对，也能让产品更清楚技术侧真正的限制。

我觉得遇到需求模糊时，最重要的不是直接说“能做”或者“做不了”，而是把问题、成本和可选方案讲清楚，先把目标对齐，再开始实现。

## 题 11. 最近在学什么 AI 技术？

最近我主要在看两块，一块是 Agent Harness，一块是 Agent 评测。

Harness 可以理解成 Agent 外面的运行框架，包括工具调用、上下文管理、状态维护、重试、日志和执行约束这些能力。我现在比较关注的是，怎么让 Agent 在复杂任务里不只是“能跑”，而是跑得稳定，出了问题还能定位和复现。

另一块是 Agent Evaluation。传统模型评测更多看单轮准确率，但 Agent 还要看任务完成率、工具调用是否正确、步骤是否合理、有没有死循环，以及成本和延迟。我最近比较关注用 Trace 记录完整执行链路，再结合自动评测和人工 Bad Case 分析，判断问题到底出在 Prompt、模型、工具还是流程设计上。

我觉得这两块都比较偏 Agent 真正进入生产之后会遇到的问题，所以最近投入比较多。

## 题 12. 平时怎么学习 Agent / LLM？

我学 Agent 和 LLM 基本是“先理解原理，再看成熟实现，最后用项目验证”。

一方面我会看经典论文、官方文档和一些比较成熟的开源项目，比如 Function Calling、RAG、Memory、MCP、ReAct 这些。看的时候我不太会只记概念，更关注它到底解决什么问题、适合什么场景、边界在哪里。

另一方面我会直接看框架或者开源项目的实现，比如它们怎么做工具调用、上下文管理、状态维护和错误重试。遇到比较感兴趣的能力，我通常会先跑一个最小 Demo，再放到真实任务里测试。

所以我的学习方式比较偏边学边做。我希望最后不只是知道一个技术“是什么”，而是能通过实际结果判断它到底有没有解决问题。

## 题 13. 为什么选择 Agent 开发？

我选择 Agent 开发，主要是因为我觉得它比单纯做聊天模型更接近真实业务。

现在大模型本身能力已经很强，但真正让它完成一个业务任务，还要处理工具调用、任务规划、上下文管理、Memory、异常重试和评测这些问题。我比较喜欢这种既需要理解模型能力，又需要做工程系统设计的方向。

而且我觉得 Agent 最终评价标准不是“回答得像不像”，而是能不能真正完成任务、正确调用工具、稳定运行，出了问题以后还能定位和优化。

我之前也做过多模态和 Agent 相关项目，所以后面希望继续往这个方向深入，做真正能上线、能评测、能长期迭代的 Agent 系统，而不是只停留在 Demo 层面。

## 题 14. 为什么选择携程？

我觉得旅游场景本身就非常适合 Agent 落地。一次旅行往往不是一个单轮问题，而是从理解需求开始，还要经过搜索、行程规划、酒店和机票推荐、信息查询，甚至后续订单操作，本身就是一个多步骤、多工具、多轮交互的任务。

另外我比较看重携程有真实而且完整的业务场景。Agent 做出来以后，不只是看 Demo 效果，还可以通过任务完成率、用户反馈、延迟和成本这些指标持续评测和优化，这和我现在比较关注的 Agent Trace、Harness 和评测方向也比较匹配。

我之前一直在做多模态和 Agent 相关项目，所以我希望下一步能参与一个真正上线、服务真实用户、长期迭代的 Agent 系统。我觉得携程的业务场景和我的方向契合度比较高。

## 题 15. 挑一个项目讲清楚你负责了什么

我可以讲一下教辅录题项目，这个项目从方案到核心流程我参与得比较完整。

业务上原来主要靠人工从教辅 PDF 里录入题目，一本书页数多、结构也比较复杂，录完以后还要再对照原书检查。我主要做的是把解析、切题、质检、人工确认和入库串成一条能够持续运行的流程。

我重点做了三件事。

第一是切题时怎么用模型。我没有让模型直接生成题目，而是让它判断题干、选项、答案和解析对应哪些版面区域，正文由程序从原文回填。这样结果可以回到原图核对，不确定的内容也可以交给人工处理。

第二是质检流程。第一版直接让文本模型判断并修改，效果不稳定。后来我把它拆成文本模型发现可疑项、视觉模型对照原图复核、写回前做位置和版本校验三步，高风险情况交给人工。

第三是工程上的稳定性。切题、识别和质检都可能运行比较久，所以我把流程做成异步执行，支持失败续跑和成功结果复用，同时保留模型版本和原始返回，方便后续定位问题。

结果上，平台累计接入大约 6862 本教材、72.9 万页、125.2 万道题；解析稳定跑了 2225 本，质检覆盖 80 本、14.4 万道题，抽检时间从一本大约 40 分钟降到了 18 分钟左右。
