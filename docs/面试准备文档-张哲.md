#### 面试官可能问的问题

**Q1: 为什么用 FAISS 的 IndexFlatIP 而不是 HNSW/IVF？**

> 模型库规模在几千级别，`IndexFlatIP` 暴力搜索在这个量级下延迟 < 10ms，完全不需要近似索引。近似索引（HNSW/IVF）的优势在百万级以上才体现，而且会牺牲精度。对于模型管理平台这种非实时高并发场景，精度比极致性能更重要。

**Q2: 原子快照写入的具体流程？**

> 代码在 `FaissIndexStore._write_snapshot()`（`vector_service.py:447-465`）：
> 1. 在 staging 目录下创建临时目录
> 2. 将新索引写入临时目录的 `faiss_index.bin`
> 3. 写入 meta JSON，`flush()` + `os.fsync()` 确保落盘
> 4. `os.replace()` 原子替换到正式路径（POSIX 保证原子性）
> 5. `os.fsync()` 目录，确保目录元数据落盘
> 6. 清理临时目录
>
> 如果任何步骤崩溃：步骤 1-3 之间崩溃，临时文件残留，不影响正式索引；步骤 4 之前崩溃，旧索引完好；步骤 4 是原子的，要么全成功要么全失败。

**Q3: Django Signal 做增量索引有什么坑？你怎么处理的？**

> 代码中（`signals.py:21-28`）每个 Signal handler 都有 try-except + 日志：
> ```python
> try:
>     vector_service.upsert_models_by_ids([model_id])
> except Exception as exc:
>     logger.error("模型索引更新失败，model_id=%s, error=%s", model_id, exc, exc_info=True)
> ```
> 主要坑点：
> 1. **Signal 异常会静默吞掉**：Django 默认不传播 Signal 异常，必须自己 try-except + 日志
> 2. **批量操作触发 N 次 Signal**：用 `bulk_create` 时不发 Signal，批量完成后手动触发
> 3. **事务回滚**：用 `transaction.on_commit()` 延迟 Signal 到事务提交后

**Q4: 搜索时读写并发怎么处理的？**

> 代码中（`vector_service.py:644-666`）维护了一个独立的 `_search_index` 副本：
> ```python
> def _publish_search_index(self, index, meta):
>     self._search_index = self.index_store._clone_index(index)
> ```
> - 写入操作修改 `self.faiss_index`，完成后调用 `_publish_search_index` 更新搜索副本
> - 搜索操作使用 `_search_index` 副本，通过 `_load_search_snapshot()` 获取
> - 所有操作由 `threading.RLock` 保护
> - 本质是"写入时复制"（Copy-on-Write），读操作完全无锁

**Q5: 模型名重复 4 次是什么原理？**

> 代码在 `RetrievalTextBuilder.build_model_document()`（`vector_service.py:268`）：
> ```python
> lines = [
>     *[f"模型名称: {model_name}" for _ in range(self.name_repeat_count)],
>     ...
> ]
> ```
> 原理：FAISS 内积搜索时，文档向量是各字段 embedding 的聚合。模型名重复 4 次相当于给名称字段 4 倍权重，让名称匹配在语义搜索中占更大比重。这是一种简单有效的 query-document 交互增强技巧，比在 embedding 层面做加权更直接。

### 3.2 核心架构：LangGraph StateGraph（`agentbot/core/agent.py:162-177`）

```python
def create_agent_app(provider_name, model_name, tools, checkpointer):
    # 1. 组装工具：内置 12 个 + 动态加载 skills
    actual_tools = BUILTIN_TOOLS + load_dynamic_skills()
    tool_node = ToolNode(actual_tools)

    # 2. 绑定工具到 LLM
    llm = get_provider(provider_name, model_name)

    # 3. 构建图
    workflow = StateGraph(AgentState)
    workflow.add_node("agent", agent_node)
    workflow.add_node("tools", tool_node)
    workflow.add_edge(START, "agent")
    workflow.add_conditional_edges("agent", tools_condition)  # LangGraph 内置路由
    workflow.add_edge("tools", "agent")

    # 4. 编译（带 Checkpointer 持久化）
    return workflow.compile(checkpointer=checkpointer)
```

**图结构**：`START → agent → [tools_condition] → tools → agent → ... → END`

### 3.3 agent_node 核心逻辑（`agentbot/core/agent.py:35-160`）

每次进入 agent_node 时执行：

1. **审计工具结果**：反向扫描 messages 中的 `tool` 类型消息，逐条写入审计日志
2. **上下文裁剪**：调用 `trim_context_messages(messages, trigger_turns=40, keep_turns=10)` —— 超过 40 轮时只保留最近 10 轮
3. **摘要压缩**：被丢弃的消息送给 LLM 生成摘要，与已有摘要合并，用 `RemoveMessage` 从状态中删除旧消息
4. **加载用户画像**：读取 `workspace/memory/user_profile.md`，注入 system prompt
5. **组装 system prompt**：核心对话原则 + 沙盒安全协议 + 用户长期画像 + 近期对话摘要
6. **调用 LLM**：`llm_with_tools.invoke(msgs_for_llm)`
7. **审计日志**：记录 `tool_call` 或 `ai_message` 事件

### 3.10 面试官可能问的问题

**Q10: LangGraph StateGraph 的 agent ↔ tools 循环具体怎么工作的？**

> 图结构是 `START → agent → [条件边] → tools → agent → ... → END`。agent 节点调用 LLM（已 bind_tools），LLM 返回的 message 如果包含 `tool_calls`，LangGraph 内置的 `tools_condition` 自动路由到 tools 节点；如果不包含，路由到 END。tools 节点是 `ToolNode`（LangGraph prebuilt），自动解析 tool_calls、执行工具、返回 ToolMessage。然后无条件回到 agent 节点，LLM 看到工具结果后决定下一步。

**Q11: 上下文裁剪为什么选 40 轮触发、保留 10 轮？**

> 这是实验调出来的平衡点。40 轮之前大多数模型的上下文窗口都够用，不需要裁剪。触发后保留 10 轮是保证近期对话连贯性的最小量——太少会导致 LLM "失忆"，太多则压缩效果不明显。摘要压缩后 Token 用量降低约 60%，这个数字是通过实际测试验证的。

**Q12: 摘要压缩和长期记忆怎么分工？**

> 摘要只管"近期对话说了什么"，长期画像只管"用户是谁、偏好什么"。摘要在 system prompt 中有明确约束："绝对不要记录用户的静态偏好"。这样分工避免了信息重复和冲突——用户画像跨会话保留，摘要随会话结束丢弃。

**Q13: 多模型适配中，不同 provider 的 tool calling 格式差异怎么处理？**

> 所有 OpenAI 兼容的 provider（阿里云、智谱、腾讯混元等）都用 `ChatOpenAI`，tool calling 格式天然一致。Anthropic 用 `ChatAnthropic`，LangChain 内部做了格式转换。Ollama 用 `ChatOllama`，部分模型 tool calling 支持不完整，实际使用中会降级为纯文本模式。关键设计是统一用 `llm.bind_tools()` 绑定工具，LangChain 负责底层格式适配。

**Q14: 定时任务的心跳注入是怎么设计的？**

> 这是一个比较巧妙的设计（`agentbot/core/heartbeat.py`）。`pacemaker_loop` 每 10 秒扫描 `tasks.json`，找到到期任务后，不是单独执行，而是将系统消息注入到 Agent 的 `task_queue` 中。Agent 通过完全相同的 LangGraph 循环处理这条消息——LLM 看到"提醒：xxx 任务到期"，可以决定调用工具或回复用户。这样不需要单独的任务执行引擎，架构简洁。

**Q15: 动态技能的"两阶段调用"是什么？**

> 从 `workspace/office/skills/` 加载的 `SKILL.md` 文件会被包装为工具。LLM 调用时先 `mode='help'` 读取完整手册（最多 3000 字符），理解技能功能后再决定是否 `mode='run'` 执行。实验数据（`tests/test_two_phase_skills.py`）显示这能将误操作率从 50% 降到 10%，代价是决策时间增加约 23.5%。这是一个安全性和效率的权衡。

**Q16: 沙盒安全有哪些层次？**

> 三层防护：
> 1. **路径解析层**：`_get_safe_path()` 用 `os.path.abspath` + `startswith` 校验，拦截 `../` 穿越
> 2. **正则拦截层**：5 条正则匹配危险命令模式（绝对路径、home 目录、Windows 盘符等）
> 3. **System Prompt 层**：在 system prompt 中明确禁止 jailbreak、单行解释器、外部目录脚本
>
> 局限性：`calculator` 工具用 `eval()` 有理论风险（虽然限制了 `__builtins__`），Shell 用 `shell=True` 也有固有风险。这些在代码注释中有标注，适合本地 CLI 工具的安全级别。

```python
class Agent:
    def run(self, user_prompt):
        for round_num in range(1, self.max_rounds + 1):
            result = self.llm.stream_chat(messages, tools=tools_schema)
            if result["tool_calls"]:
                # ThreadPoolExecutor 并行执行（max 8 workers）

         → 下载 ZIP 结果 → 提取 content_list.json
         → 合并（页码重索引）→ 存储到本地
```

**MinerU API Key 池管理**（`mineru-key-pool.service.ts`）：
- 加权随机选择
- 每 key 并发限制（`maxConcurrent`）
- 冷却期：瞬时失败 2 分钟，配额耗尽 15 分钟
- 自动健康探测（每 24 小时）
- 指数移动平均跟踪耗时（70% 历史 + 30% 最新）

#### Phase 2：LLM 题目抽取（`recording.ts:2059-2984`）

两种任务类型，通过 BullMQ 队列执行：

**auto-catalog（目录识别）**：
- 读取 MinerU `content_list.json`
- LLM 识别章/节/课时层级结构
- 返回三级目录树

**auto-cut（题目切割）**：
- 按章节目标获取 MinerU 源数据
- LLM 按 XML 格式抽取：`<chapter>` → `<qa_pair>` → `<question>`/`<options>`/`<answer>`/`<solution>`

**分块处理**：
- 用 `js-tiktoken`（cl100k_base）计算 token 数
- 超过 128K 字符递归拆分
- 并行处理多个分块

#### 面试官可能问的问题

**Q21: PDF 双栏查看器的性能优化？**

> 2189 行的 `DoublePdfViewer.vue` 做了几个关键优化：
> 1. **LRU 页面缓存**：250MB 限制，Blob URL 存储，避免重复渲染
> 2. **按需渲染**：只渲染可视区域 ± 预加载 2 页
> 3. **Canvas 复用**：缩放时复用 canvas 元素，只改变尺寸
> 4. **坐标归一化**：标注框用 1000×1000 相对坐标，缩放时无需重新计算
> 5. **虚拟滚动**：标注层只渲染可视区域内的 annotation boxes

**Q22: MinerU 集成中最大的挑战？**

> 大 PDF 的处理。MinerU 有 200MB/600 页的限制，但教辅 PDF 经常超过这个限制。解决方案是用 `qpdf` 自适应拆页——根据文件大小和页数计算最优分块大小，递归二分处理超大块。另一个挑战是 API Key 的并发管理——多个用户同时上传时会抢 Key，所以做了 Key Pool 的加权选择 + 并发限制 + 冷却期机制。

**Q23: 自动切题的 LLM prompt 怎么设计的？**

> 核心是结构化输出。用 XML 格式约束 LLM 输出（`<chapter>` → `<qa_pair>` → `<question>`/`<options>`/`<answer>`/`<solution>`），因为 XML 比 JSON 更适合嵌套结构，而且 LLM 对 XML 的格式遵循度更高。同时做了兜底——LLM 解析失败时用正则按题号模式（"1."、"（1）"等）分组，保证系统不会完全不可用。

**Q24: 草稿系统的 revision 冲突怎么处理？**

> 乐观锁机制（`recording-draft-sync.service.ts`）：
> 1. 每次保存携带 `baseRevision`
> 2. 服务端对比当前 revision，不匹配返回 409
> 3. 前端收到 409 后提示用户"草稿已被其他会话更新"，让用户选择覆盖或放弃
> 4. 同时有每小时的历史快照（`RecordingDraftHistory`），极端情况下可以恢复

**Q25: ops-monitor 的 Worker 心跳怎么实现的？**

> 每个 Worker 启动时生成 `instanceId`（UUID），每 10 秒向 Redis 写入心跳：
> ```typescript
> // Key: worker:heartbeat:{queueName}:{instanceId}
> // Value: { heartbeatAt, hostname, pid, activeJobs, concurrency, ... }
> // TTL: 30 秒
> ```
> ops-monitor 定期扫描所有心跳 key，超过 30 秒未更新的判定为离线。同时记录每个 Worker 的最后任务开始/结束时间，用于判断 Worker 是否卡死。

**Q26: 简历上说用了 Element Plus，实际用的是 Ant Design Vue？**

> 项目基于 Vben Admin Pro 框架，它支持多 UI 库切换。实际部署用的是 Ant Design Vue 版本（`web-antd`），但项目也保留了 Element Plus 版本（`web-ele`）的代码。我在简历中写 Element Plus 是因为它是我更熟悉的 UI 框架，在二十八所的实习项目中也是用的 Element Plus。

## 六、常见行为面试题

### Q: 最有挑战性的项目？

> AgentBot 的记忆系统最有挑战性。双层水位设计——短期记忆用 SQLite Checkpointer 存完整对话，长期记忆用 Markdown 文件存用户偏好——看起来简单，但上下文裁剪的触发时机和保留轮数调了好几版。40 轮触发 + 保留 10 轮这个参数是实验出来的，太早触发浪费计算，太晚触发超 context window。摘要压缩的 prompt 也迭代了多次，关键是要让 LLM 区分"近期对话内容"和"用户静态偏好"，前者归摘要管，后者归 user_profile.md 管。

### Q: 遇到过的技术难题？

> 二十八所实习时，FAISS 索引的并发安全是个难题。最初方案是读写锁，但写操作（索引重建）耗时 30s+，期间所有读请求阻塞。后来改成 Copy-on-Write 方案——维护独立的搜索索引副本，写入完成后原子切换。读请求完全无锁，写入也不阻塞读取。这个经历让我深刻理解了"先保证可用性，再优化性能"的工程原则。

### Q: 怎么学习新技术？

> 项目驱动。AgentBot 和 WikiAgent 两个项目就是很好的例子——AgentBot 用 LangGraph 追求工程化，WikiAgent 从零实现 ReAct 循环追求理解深度。两个项目做完，我对 Agent 开发有了从底层机制到框架使用的完整认知。遇到问题再回去查文档和源码，这样学得深。

### Q: 对 Agent 方向的理解？

> Agent 的核心是"让 LLM 能做事而不只是说话"。关键能力：工具使用、规划与推理、记忆管理、安全可控。目前 Agent 的瓶颈不在模型能力，而在工程化——怎么让 Agent 稳定、安全、可观测地运行。这也是我两个 Agent 项目重点解决的问题：AgentBot 做了工具安全沙箱和 JSONL 审计日志，WikiAgent 做了子智能体权限模型和知识库一致性维护。
