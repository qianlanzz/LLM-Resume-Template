## 一、语义检索模块

### 技术细节

**问题背景**：模型资源数量增长后，关键词检索召回率下降，用户用自然语言描述任务需求时无法匹配到合适模型。

**方案**：
- 使用 `Qwen3-Embedding-0.6B` 将模型元数据（名称、描述、标签、任务类型）编码为向量
- 使用 `FAISS`（Facebook AI Similarity Search）构建向量索引，支持余弦相似度检索
- 用户输入自然语言任务描述 → 同模型编码为查询向量 → FAISS ANN 检索 Top-K

**增量索引更新**：
- 通过 `Django Signal`（`post_save` / `post_delete`）监听模型元数据变更
- 变更触发异步任务重建受影响的索引分片（增量，非全量重建）

**并发安全**：
- 索引读写采用**快照隔离**：写操作先构建新索引对象，完成后原子替换旧对象的引用
- 持久化通过**原子文件替换**：先写临时文件，完成后 `os.replace()` 替换目标文件，保证崩溃一致性

### 面试问题

**Q1：为什么选 FAISS 而不是 Elasticsearch 的向量检索？**

> FAISS 是纯内存向量库，延迟极低（毫秒级），适合中等规模（百万以内）的向量检索。ES 的向量检索（kNN）需要额外的集群维护成本，且在小规模场景下延迟反而更高。我们的模型库规模不大，FAISS 足够，且部署更简单。

**Q2：Django Signal 触发增量索引，如果短时间内大量模型同时更新，会不会有问题？**

> 会有重复触发的问题。实际处理方式是在 Signal handler 里只发送一个 Celery 异步任务，Celery 端用任务去重（`task_id` 固定为索引分片 ID），短时间内多次触发只会执行一次重建。

**Q3：什么是快照隔离？你是怎么实现的？**

> 快照隔离指读操作始终读到一个一致的数据版本，不会读到写操作的中间状态。我的实现是：FAISS 索引对象存在一个全局变量里，写操作在内存中构建完整的新索引对象后，用一次赋值替换旧引用。Python GIL 保证单次赋值是原子的，所以读线程要么读到旧索引，要么读到新索引，不会读到半构建状态。

**Q4：Qwen3-Embedding-0.6B 是怎么部署的？推理延迟如何？**

> 用 `sentence-transformers` 加载，部署在同一台服务器上，CPU 推理。0.6B 参数量较小，单条文本编码约 20-50ms，批量编码吞吐量更高。如果延迟要求更高可以换 GPU 或用 ONNX 量化版本。

**Q5：向量检索的召回率如何评估？**

> 构建了一个测试集：人工标注了若干"任务描述 → 期望模型"的配对，用 Recall@K（K=5/10）衡量检索质量。上线前对比了关键词检索和语义检索的 Recall@10，语义检索提升约 30%。

## 二、混合推荐引擎

### 技术细节

**三路融合**：
1. **协同过滤**：基于用户-模型使用历史矩阵，计算用户相似度，推荐相似用户使用过的模型（User-based CF）
2. **内容匹配**：基于当前用户的任务标签偏好，与模型标签做 Jaccard 相似度匹配
3. **热度排序**：全局模型使用频次加权，兜底保证冷启动时有结果

**Redis 缓存策略**：
- 推荐结果按 `user_id` 为 key 缓存，TTL 设置为 30 分钟
- **主动失效**：用户有新的模型使用行为时，通过事件驱动（Celery task）主动 `DELETE` 对应 key，而非等 TTL 过期
- **写入优化**：Redis Pipeline 批量写入，减少网络 RTT
- **缓存穿透防护**：缓存未命中时，用 Redis 分布式锁（`SET NX EX`）确保只有一个 Worker 回填，其他请求等待锁释放后读缓存

**Celery 异步回填**：缓存未命中时不阻塞 HTTP 请求，而是立即返回降级结果（热度排序），同时触发 Celery 任务异步计算完整推荐结果并写入缓存。

### 面试问题

**Q1：缓存穿透、缓存击穿、缓存雪崩分别是什么？你处理了哪些？**

> - **穿透**：查询不存在的 key，每次都打到数据库。处理方式：对空结果也缓存（短 TTL）。
> - **击穿**：热点 key 过期瞬间大量并发请求同时打到数据库。处理方式：分布式锁，只让一个请求重建缓存。
> - **雪崩**：大量 key 同时过期。处理方式：TTL 加随机抖动（`30min ± random(5min)`）。
> 
> 我主要处理了击穿问题（分布式锁 + 异步回填）。

**Q2：Redis 分布式锁用 SET NX EX 有什么问题？**

> 主要问题是锁超时时间难以估计：如果业务执行时间超过 EX，锁自动释放，其他进程会拿到锁，导致并发问题。更健壮的方案是用 Redlock 或者在释放锁时校验 value（只释放自己加的锁）。我的场景是推荐计算，超时时间设置得比较宽松（10s），实际计算通常在 1s 内完成，风险可控。

**Q3：协同过滤在用户量少时效果怎么样？**

> 冷启动问题是协同过滤的固有缺陷。用户量少时相似用户矩阵稀疏，推荐质量差。我的处理是三路加权融合，协同过滤权重在用户历史行为少于 5 次时降为 0，完全依赖内容匹配和热度排序兜底。

## 三、异常检测与容量预警

### 技术细节

**5 维指标**：CPU 使用率、内存使用率、磁盘 I/O、网络带宽、HTTP 请求延迟

**DBSCAN 异常检测**：
- 定期（每 5 分钟）采集最近 1 小时的指标数据，构成 5 维时序特征矩阵
- 用 `sklearn.cluster.DBSCAN` 聚类，`eps` 和 `min_samples` 通过历史数据调参
- DBSCAN 输出 `-1` 的点为噪声点，即异常时段
- 相比阈值告警，DBSCAN 能识别多维度联合异常（如 CPU 正常但延迟异常高）

**线性回归趋势外推**：
- 对每个指标用最近 24 小时数据做线性回归（`numpy.polyfit`）
- 外推未来 2 小时的预测值
- 预测值超过容量阈值（如磁盘 85%）时生成预警工单

### 面试问题

**Q1：为什么用 DBSCAN 而不是简单的阈值告警？**

> 阈值告警需要人工设定每个指标的上下界，维护成本高，且无法捕捉多维度联合异常。DBSCAN 是无监督聚类，不需要标注数据，能自动识别偏离正常模式的时段。缺点是 `eps` 参数敏感，需要定期用新数据重新调参。

**Q2：DBSCAN 的 eps 参数怎么选？**

> 用 k-distance 图（k=min_samples）：对每个点计算到第 k 近邻的距离，排序后画图，找"肘点"作为 eps。实际操作中用历史 2 周的正常数据跑一遍，找到能把正常数据都归为一个簇的最小 eps。

**Q3：线性回归预测资源用量，准确吗？**

> 线性回归只适合趋势平稳的场景，对周期性波动（如每天业务高峰）效果差。我的使用场景是磁盘用量（通常单调增长），线性回归比较合适。对于 CPU/内存这类有周期性的指标，更好的方案是 Prophet 或 SARIMA，但复杂度更高，当前阶段线性回归够用。
