## 第一部分：DFT 快问快答 75 题（每题一句话）

### A. 数字电路与 RTL

1. **组合逻辑 vs 时序逻辑？** — 输出只依赖当前输入 vs 依赖当前输入与历史状态（含时钟沿采样）。
2. **锁存器和触发器的区别？** — 电平敏感（透明期跟随输入）vs 边沿敏感（只在沿采样）。
3. **为什么扫描链避免用锁存器？** — 透明期数据可穿透，造成移位竞争，破坏链的移位关系。
4. **阻塞赋值和非阻塞赋值？** — `=` 立即生效、按顺序执行，用于组合逻辑；`<=` 在时刻末统一更新，用于时序逻辑。
5. **什么时候会综合出 latch？** — 组合 always 块中分支未覆盖所有输出赋值。
6. **建立时间？** — 时钟沿到来前数据必须稳定的最短时间。
7. **保持时间？** — 时钟沿到来后数据必须继续保持稳定的最短时间。
8. **建立违例能不能靠降频解决？** — 能（周期变长）。
9. **保持违例能不能靠降频解决？** — 不能（保持检查式子里没有周期项）。
   这里的“变得太早”，是指：时钟沿刚到，触发器还没完成对旧数据的采样，输入就变成了新数据。
10. **亚稳态是什么？** — 输入违反 setup/hold 时，触发器输出在中间电平停留的不确定状态。
11. **亚稳态怎么处理？** — 同步器降低发生概率，不能消除；两级同步器把 MTBF 提升几个数量级。
12. **两级同步器能同步多比特吗？** — 不能，多比特要用格雷码、握手或异步 FIFO。
13. **同步复位 vs 异步复位？** — 同步复位无亚稳态风险但要求复位脉宽大于周期；异步复位即时生效但有释放亚稳态风险。工程常用「异步复位、同步释放」。
14. **CDC 路径在 STA 里怎么处理？** — 设 `set_false_path` 或 `set_clock_groups -asynchronous`。
15. **Moore 和 Mealy 状态机？** — 输出只由状态决定 vs 输出由状态和输入共同决定。
16. **独热码的好处？** — 译码简单、速度快、便于调试，代价是多用触发器。
17. **`wire` 和 `reg`？** — 连线（需连续驱动）vs 变量（可在 always 中赋值，不一定综合成寄存器）。
18. **综合三步？** — translate（翻译）→ optimize（逻辑优化）→ map（映射到工艺库）。
19. **综合的输入输出？** — 输入 RTL + .lib/.db 库 + SDC 约束，输出门级网表 + 时序报告 + SDF。
20. **仿真器有哪些？** — VCS、Xcelium、Questa；开源 Verilator、Icarus、cocotb。
21. **FSDB 和 VCD？** — FSDB 二进制、体积小、Verdi 原生；VCD 文本、通用但大。

### B. SCAN

22. **DFT 的第一性原理？** — 可控性 + 可观测性。
23. **SCAN 的本质？** — 测试模式下把所有触发器串成移位寄存器，直接读写内部状态。
24. **SDFF 是什么？代价多少？** — 带扫描的触发器（DFF + 2:1 MUX），**触发器自身面积**约 +15~30%（不是全芯片面积口径）。
25. **扫描四信号？** — SI（Scan In）、SO（Scan Out）、SE（Scan Enable）、CLK。
26. **SE=1 和 SE=0 分别是什么阶段？** — 1 = shift（移位），0 = capture（捕获）。
27. **一次 pattern 的三步？** — shift in（N 周期）→ capture（1 或 2 个脉冲）→ shift out（N 周期，与下次 shift in 复用）。
28. **测试时间怎么算？** — `pattern数 × (链长 + capture周期) / shift频率`。
29. **怎么降测试时间？** — 增加链数缩短链长；用片上压缩；减少 pattern 数。
30. **跨时钟域的扫描链要加什么？** — Lockup Latch（半周期延迟，防 hold 违例）。
31. **为什么加链数不能无限加？** — 受测试引脚数限制；链长要均衡（最长链决定时间）。
32. **Full scan vs partial scan？** — 全部触发器进链（高覆盖，主流）vs 部分进链（省面积，用于敏感场景）。
33. **scan chain reordering 是什么？** — P&R 阶段按物理位置重排链上触发器顺序，缩短布线，不影响功能。
34. **为什么链上要避开 X 源？** — X 会沿链传播，污染后续所有比较结果。
35. **扫描压缩的原理？** — 内部 Decompressor（XOR/LFSR）把少量引脚扩展成多条短链，Compactor（XOR/MISR）把多条链输出压缩到少量引脚。
36. **典型压缩比？** — 10×–100×。
37. **压缩会掉覆盖率吗？** — 会略降（激励自由度受限），用 compression-aware coverage 衡量。

### C. ATPG

38. **ATPG 是什么？** — 给定网表和故障列表，自动生成能检测所有故障的最小 pattern 集合。
39. **检测一个故障的三个条件？** — 激活（Excite）、传播（Propagate/Sensitize）、观测（Observe）。
40. **D 代数的五个值？** — `0`、`1`、`X`、`D`（正常 1/故障 0）、`D'`（正常 0/故障 1）。
41. **D 穿过 AND 门要给什么？** — 其他输入给 1（非控制值）；OR 门给 0。
42. **ATPG 算法演进？** — D-Algorithm → PODEM → FAN → SOCRATES → SAT-based（现代混合）。
43. **PODEM 相比 D 算法的改进？** — 只在原始输入上做决策，减少无效搜索。
44. **FAN 的核心思想？** — 把搜索限制在 fanout 点（head line），减少回溯。
45. **SAT-based ATPG 的优势？** — 判定冗余故障（UNSAT）能力强；缺点是资源开销大。
46. **Stuck-at 故障是什么？** — 某根线永久固定在 0（SA0）或 1（SA1）。
47. **为什么 stuck-at 模型有效？** — 抽象的纯逻辑模型，实践证明确实能覆盖大量真实物理缺陷。
48. **故障等价？** — 两个故障在所有输入向量下输出响应完全相同，测试集相同，只测一个。
49. **故障支配？** — 能测 f2 的向量一定能测 f1（反之不然），则测 f2 即可。
50. **故障压缩（collapsing）？** — 用等价和支配关系缩减故障列表。
51. **TDF 是什么？** — 跳变延迟故障：线在应该跳变时超出时间窗才跳变（STR / STF）。
52. **LOC 和 LOS？** — Launch-On-Capture（两个功能脉冲，主流）vs Launch-On-Shift（最后一个 shift 沿 launch，覆盖更高但 SE 难高频）。
53. **TDF 覆盖率为什么低于 stuck-at？** — 需要建立正确跳变、需要 at-speed 路径可用、X 影响更严重。
54. **OCC 是什么？** — 片上时钟控制器，负责在 shift 慢时钟和 capture 高速脉冲之间无毛刺切换。
55. **覆盖率公式？** — `DT_eff = DT + credit×PD`（**credit 默认 50%**，`set_possible_credit` 可调）；`FC = DT_eff/FU`、`TC = DT_eff/(FU−UT)`。分类代数（表 3-21）：`FU=TE+UT`、`TE=DT+PD+AU+UD`、`UT=UU+TI+BL+RE`，**AU 属 TE、保留在分母**。实测用 `DT+0.5×PD` 能逐位复现手册报告。
56. **DT / PT / AU / UD / UU / TI / BL / RE？** — 已检测 / 可能检测 / ATPG 判定不可测 / 未检测 / 未使用 / 被tie住 / 被阻塞 / 冗余。（**UT = 不可测 = UU+TI+BL+RE，不是"未测试"**，别被命名坑。）
57. **覆盖率上不去的排查顺序？** — AU 分布 → X 源 → DRC 违反 → ATPG effort/abort limit → 最后才加测试点。
58. **X 怎么处理？** — X-bounding（强制确定值）、X-masking（屏蔽通道）、测试点/bypass。
59. **测试功耗问题？** — shift 翻转率高导致 IR-drop 和良率损失；capture 是功耗峰值。缓解：low-power ATPG、分组移位、降低 shift 频率。
60. **Pattern 交付格式？** — STIL（IEEE 1450，主流）、WGL、VCD/EVCD、Verilog TB。

### D. MBIST / 存储器

61. **存储器为什么不能进扫描链？** — 阵列结构非标准触发器 + 故障模型不同（耦合/译码/图形敏感）。
62. **MBIST 五组件？** — 地址生成器、数据生成器、期望数据寄存器、比较器、控制 FSM。
63. **MBIST 三个关键信号？** — BIST_GO、BIST_DONE、BIST_FAIL。
64. **MBIST 何时跑？** — 晶圆测试（CP）、最终测试（FT）、上电自检（POST）。
65. **Transparent MBIST？** — 读-暂存-测-写回，运行中不破坏存储内容，车规/航天用。
66. **March 记法？** — `⇕(w0)` 方向无关；`⇑` 升序；`⇓` 降序；括号内对同一地址顺序执行。
67. **March C− 的元素？** — `{⇕(w0); ⇑(r0,w1); ⇑(r1,w0); ⇓(r0,w1); ⇓(r1,w0); ⇕(r0)}`，复杂度 **10N**。
68. **MATS+ 复杂度？** — **5N**（`1+2+2`）。⚠️ 复杂度按**操作次数**求和，不按元素个数；March C− 是 **6 个元素 / 10N**。
69. **March SS 复杂度？** — 22N，覆盖全部**静态简单**故障（**不含 NPSF**）。不能说"最强"——March AB 同为 22N，March RAW 26N，NPSF 专用算法更高。
70. **March 算法为什么有效？** — 升/降序制造相邻单元耦合，读后写制造跳变。**注意：测 NPSF（邻域图形敏感故障）要靠棋盘格/条纹图形或专用算法（68N/96N），不是 March 序列本身。**
71. **算复杂度要注意什么？** — 先澄清 N 是 bit 数还是 word 数。
72. **BISR 是什么？** — 内建自修复，用冗余行/列 + eFuse 记录替换信息，提升良率。
73. **LBIST 的核心结构？** — PRPG（LFSR 伪随机激励）+ MISR（签名压缩）+ 控制 FSM。
74. **LBIST 的弱点？** — 随机图形覆盖不了难测故障、对 X 极敏感、面积和功耗大。
75. **为什么有 LBIST 还要 ATPG？** — 确定性图形覆盖率永远高于随机图形；实际用 mixed-mode BIST。

## 第二部分：遇到不会的问题怎么办

**这是整份资料里最实用的一节。** DFT 覆盖面极广（前端、后端、ATE、工艺、模拟），**没有一个候选人能全答上来**。面试官看的不是你知不知道，而是**你面对未知的态度**。

### 三种安全答法（按优先级）

**① 说出边界 + 给出思路（最好）**

> "这个具体细节我不确定。但按我理解，问题应该落在 XX 这一类，如果是这样的话，我会先查 A，再看 B。"

**② 关联已知（次好）**

> "我没做过这个，但它和我了解的 XX 有点像——XX 里是用 YY 解决的，不知道这里是不是同一个思路？"

**③ 坦诚 + 追问（兜底，永远可用）**

> "这个我确实不知道，能麻烦您说一下吗？我想学一下。"

**③ 一点都不丢分。** 面试官经常反而因为这句话开始给你讲——**他在讲的过程中，你有机会展示理解力和追问能力**，这比硬编答案得分高。

### 绝对不要做的三件事

1. **编造术语或数字。** 面试官是这个领域的，一句假话就废掉整场信任。
2. **答不出就沉默或含糊带过。** 沉默会被解读为"连思路都没有"。
3. **把话题强行扯回你会的领域。** 显得不诚实，也答非所问。

### 准备三个"安全答不出来"的问题

提前想好三个你**确定不会**的方向，练习说："这块我了解得比较浅，我知道的是 X，再深就不敢乱说了。" 心里有底，现场就不会慌。

**建议选的三个方向**（都是 DFT 边缘、你不必精通的）：

- 模拟/混合信号 DFT（ADC/DAC 测试、PLL 测试）
- 先进封装测试（2.5D/3D、TSV 测试）
- 具体 ATE 机台的编程细节（TDS、时序设置、pin electronics）

## 第三部分：主动提问（面试最后一定会问"你有什么想问的"）

**问什么，决定面试官对你的最终印象。** 好的提问展示你已经在用 DFT 工程师的思维思考问题。

### 强烈推荐的 5 个问题

1. **"团队目前用的是哪套 DFT 流程和工具链？TetraMAX 还是 Tessent？"**
   → 展示你知道工具名，且关心实际工作方式。
2. **"这个岗位主要负责前端（scan/ATPG）还是全流程？会参与 RTL 阶段的可测性 review 吗？"**
   → 展示你知道 DFT 有多种分工。
3. **"团队的覆盖率目标和测试时间预算是多少？"**
   → 这个问题非常专业。它说明你理解 DFT 的核心权衡是**覆盖率 vs 测试成本**。
4. **"新人在前几个月一般从什么工作开始？有没有导师或者培训流程？"**
   → 展示你打算长期做，且对成长路径有预期。
5. **"团队规模多大？DFT 和设计、后端、测试部门的协作方式是怎样的？"**
   → 展示你理解 DFT 是跨部门角色。

### 不要问的

- 薪资、加班、调休（等 HR 面）
- "我能不能做 AI 相关的方向"（会暴露你只是把 DFT 当跳板）
- 网上能查到的公司基本情况（显得没做功课）

## 第四部分：自我介绍模板（DFT 版，60–90 秒）

> 各位面试官好，我叫张哲，南京理工大学软件工程专业硕士在读。
>
> 我先说明一下我的背景和这个岗位的匹配逻辑，因为我猜您会关心这一点。我本科硕士都是软件工程，项目经历偏软件工程和大模型应用，但我投 DFT 是经过考虑的，主要有三点。
>
> 第一，DFT 前端有大量工程化和自动化的工作。跑 ATPG、门级仿真、批量做 scan rule check、把覆盖率报告做成可对比的看板、做回归定位——这些本质上是大批量任务调度加日志分析加数据聚合。我在教辅项目里做的是 BullMQ 任务队列、断点续跑、幂等去重、Prometheus 监控 P95 和队列积压，方法论完全一样，只是对象从 PDF 变成网表。
>
> 第二，DFT 的原理我已经系统补过。可控性和可观测性、SCAN 的 shift 和 capture 过程、D 代数和 ATPG 算法、stuck-at 和 transition 故障模型、March 算法和 MBIST 架构，这些我能讲清楚原理，不是只知道名词。
>
> 第三，我的调试方法论是可迁移的。我做过长任务和分布式系统的排障，习惯先找最小复现单元再逐层排除。DFT 里 debug pattern fail、定位 X 源、分析覆盖率缺口，是同一套方法。
>
> 我不回避短板：我没有产线级的 EDA 工具实操经验，也需要时间补后端和 ATE 这块。但如果您需要的是一个能把流程工具化、能处理大规模数据、同时又理解 DFT 原理的人，我认为匹配度是够的。
>
> 好，以上就是我的自我介绍。

**要点**：

- **第一句就主动解释"专业不对口"**，不要等面试官问。等被问了再解释，显得被动。
- 结构化（三点），面试官好记。
- 主动说短板，比藏着强。
- 全程控制在 90 秒内。

## 第五部分：简历风险与修改建议

我在读 `resume-zhangzhe-dft.tex` 时发现几个**投 DFT 岗位时的结构性风险**，供参考：

### 风险 1：DFT 内容占比太低（最严重）

**现状**：全文 110 行，DFT 相关内容只有**关键词行 + 摘要一句 + 专业技能里 2 条**，其余全是软件/Agent/AI 项目。

**面试官视角**：这份简历看起来像是"AI 简历改了关键词投 DFT"，会很自然地怀疑投递诚意。

**建议**（按投入产出排序）：

1. **在摘要里补一句主动的解释**。现在的摘要只说「求职 DFT 工程师方向」，缺乏说服力。可以改成：

   > "……求职 DFT 工程师方向。**具备软件工程与自动化能力，并系统学习过数字电路、SCAN/ATPG/MBIST 原理，目标是以工程化和工具链能力切入 DFT 前端流程。**"
   >
2. **技能栏的 DFT 部分加"工具链认知"**。现在只写了原理，可以补：

   > "了解 DFT 流程与主流工具链（DFT Compiler / TetraMAX / DFTMAX / Tessent），能用 Tcl / Python 做工具流程脚本与日志分析。"
   >
3. **如果时间允许，做一个小的 DFT 练习项目**（这个最有效）：

   ⭐ **推荐做这个**：用 **OpenROAD / OpenLane** 或 **Yosys + 开源 ATPG**，做一个完整的 RTL → 综合 → scan insertion → ATPG → 覆盖率报告的小流程。或者在 FPGA（Verilog）上写一个带 scan chain 的计数器，用 Python 脚本模拟 shift/capture 并生成 pattern。

   哪怕只是玩具规模，简历上写一行"独立搭建 RTL→scan insertion→ATPG 的最小流程，输出覆盖率报告"——**可信度比十条软件经历都高**。
4. **把软件经历重写成"DFT 视角"**。同样的项目，换个说法：

   - 「BullMQ 长任务调度 + 断点续跑」→ 「**大批量任务流水线调度与断点续跑**（可直接迁移到 ATPG/仿真回归流水线）」
   - 「Prometheus + Grafana 监控 P95 / 队列积压」→ 「**测试流水线指标看板与告警**（覆盖率趋势、任务积压、Worker 存活）」
   - 「日志排查与问题定位」→ 「**大规模日志解析与失败模式分析**」

   **不要编造 DFT 经历**，但可以强调能力的可迁移性。这是诚实且有效的。

### 风险 2：时间线有重叠

**现状**：

- 中电科 28 所：2025.09–2026.04
- 九方智投：2026.05–2026.08
- 教辅项目：2026.02–至今 ← **与九方智投实习重叠**

**面试官会问**："教辅项目在 2026.02 开始，那时你还在实习？"

**提前想好口径**，比如：

> "教辅项目是我从 2026 年 2 月启动的自主项目，前期是搭框架和探索，同期我在 28 所实习；5 月转去九方智投实习后，这个项目我利用业余时间继续维护。它不是全职工作，所以时间上是并行推进的。"

**如果实际情况不是这样，务必统一所有材料的口径**——简历、面试口述、背调信息不一致是最致命的。

### 风险 3：WACV / CVPR 两条只有一行

**现状**：只有比赛名和奖项，没有任何方法描述。

**风险**：面试官一定会问"这个比赛你做了什么"。答不上来会连累前面所有经历的可信度。

**建议**：每条补一行方法描述（哪怕很短）。

### 风险 4：所有项目都是"独立实现 / 主导 / 参与"，权重都很大

**风险**：面试官会怀疑注水。

**建议**：把明显是协作的部分明确写"参与"，把真正独立主导的写清边界。**诚实的分工描述比全是"主导"更可信。**
